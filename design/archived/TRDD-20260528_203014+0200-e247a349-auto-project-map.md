## 1. Problem / motivation

Every session re-reads large swaths of a codebase to learn "what does this file
/ function do" — burning tokens and producing incoherent, drifting mental
models (the janitor itself hit this: re-deriving its own architecture each
turn). A **compact, always-current project map embedded in each project's
CLAUDE.md** turns "re-read 50k lines" into "read a ~300-line map." Because
CLAUDE.md is auto-loaded every session, the map is free to consult. The janitor
is the right owner: it already runs per-session/per-project and watches for
drift — keeping a map fresh as code changes is the same shape of work.

This TRDD specs a janitor feature that **auto-generates and auto-updates a
delimited project-map section** in CLAUDE.md for any project, in any supported
language, cheaply and safely.

## 2. The format (the crux — "effective and compact")

A **hybrid** CLAUDE.md: human-authored narrative (architecture, conventions,
gotchas — the janitor NEVER touches this) PLUS one machine-maintained section
fenced by markers:

```
<+-+-JANITOR-REPO-MAP-START-(do-not-modify)-+-+> v1 sha=<rendered-hash> digest=<repo-change-digest> generated=<iso>
## Project map (auto-generated — do not edit between the fences)
`scripts/lib/state.py` — per-session state helpers (port of state.sh)
  · project_root() -> Path — resolve $CLAUDE_PROJECT_DIR / git root / cwd
  · atomic_write(path, text) — tmp+rename write
  · log_line(name, msg) — append to <state>/<name>.log
`scripts/daemon.py` — global singleton daemon
  · Task.run() — run fn, finally-stamp last-run.ts
  · task_marketplace_refresh() — bulk `claude plugin marketplace update`
...
### Convention groups
`scripts/lib/*_patterns.py` (×198) — one security pattern lib per attack class; each exposes PATTERNS consumed by scanner detectors. [cloud_credential, prompt_injection, npm_lifecycle, …]
<+-+-JANITOR-REPO-MAP-END-(do-not-modify)-+-+>
```

The fence strings are intentionally unusual (`<+-+-JANITOR-REPO-MAP-START-(do-not-modify)-+-+>`
/ `…-END-…`) so they (a) never collide with real content, (b) are a one-shot
`grep`/`sed` target for the regenerator (extract-between-fences, splice-back —
no markdown parsing, minimal tokens), and (c) loudly tell a human not to edit
inside. The START fence also carries `sha=` (rendered-map hash) and
`digest=` (repo-change digest) so the maintainer decides "regen needed?" by
reading ONE line, not the whole block.

**Compactness rules (each is load-bearing):**
1. **One line per file** = path + first line of the module docstring (its role).
2. **Indented one line per PUBLIC symbol** = name + compact signature + first
   docstring line. Private (`_`-prefixed) symbols omitted unless they're the
   only ones.
3. **Convention-collapse:** files matching a detected uniform shape (same dir,
   same exported-symbol skeleton, naming pattern) collapse to ONE group line +
   a bracketed name list — never N files × M symbols. This is what keeps a
   200-file `*_patterns.py` tree to two lines.
4. **Deterministic + sorted** (path, then source order) → a code change yields a
   minimal, reviewable diff, not a reshuffle.
5. **Content-hash header** → the maintainer recomputes the extracted structure,
   compares the hash, and **rewrites only when it changed** (token-cheap, git-quiet).
6. **Marker-fenced** → everything outside the markers (human narrative) is
   untouched, always.

**Quality bar — the map must PREVENT reasoning errors (acceptance, not a nicety):**
Coverage is worthless if descriptions are shallow. Each symbol's line MUST encode
the **load-bearing / surprising behavior a reader would otherwise get WRONG** —
not just the surface action. Spend the compactness budget exactly where it
prevents errors:
- ✗ `Task.run() — stamps last-run.ts` (reader can still assume "stamps on
  success" → concludes "stale last-run = failing task" — WRONG).
- ✓ `Task.run() — runs fn; finally-stamps last-run.ts UNCONDITIONALLY (success
  OR fail) ⇒ stale last-run = task not running, NOT failing`.

Litmus for every correctness-critical symbol: *"would this line have stopped the
daemon.py:345 mistake?"* (the false claim "stale last-run = the refresh is
failing"). If not, the line is too shallow. Encode invariants **explicitly** —
*unconditional / in-finally / atomic / idempotent / raises X / never-blocks /
single-writer*. Prefer source docstrings whose FIRST line already states the
invariant; a future "docstring-quality" signal can flag symbols whose docstrings
bury or omit it (garbage-in → garbage-map).

## 3. Architecture

- **Extractor (language-agnostic):** source the symbol data from an AST, never
  regex. Reuse `tldr structure --lang <l>` (codemaps: names + leading comments)
  and/or codegraph when a `.codegraph` index exists. Supported langs follow
  tldr: python, typescript, go, rust (extend as tldr does). One extractor
  interface; per-language adapters.
- **Renderer:** turns the extracted tree into the §2 format; does the
  convention-collapse; emits the content hash.
- **Maintainer (the janitor surface):** a per-project **detector**
  (`project-map-drift`) in the heartbeat roster — NOT a skill (detectors are the
  per-cadence sync-checkers; that's the right home). It runs each heartbeat but
  separates a **cheap every-heartbeat DETECTION** from a **deferred, cache-cost-aware
  WRITE** (the write is the expensive part — see §5):
  1. **cheap change-digest each heartbeat** — git `HEAD` + `git status --porcelain`
     digest (or max source mtime) vs the `digest=` recorded in the START fence.
     Unchanged → **instant skip, no extraction, no write.**
  2. else compute the **pending change magnitude** (Δ lines/files as % of repo)
     and store it in a `map-dirty` accumulator. **Do NOT write yet.**
  3. **the WRITE is scheduled by §5's cache-cost gate** — only fire at a
     cache-cheap moment (post-compaction / low context / idle). When the gate
     opens: extract → render → content-hash → if the rendered hash differs from
     the fence's `sha=`, **atomically** rewrite ONLY the fenced section
     (tmp+os.replace), preserving everything else byte-for-byte → clear the
     accumulator → emit a one-line note.
  - **Multi-session safety:** project-scoped (NOT a daemon op), but N sessions in
    one project are deduped by the `sha=` gate (first regen wins; others see the
    current hash and skip) + a short project-scoped gen-lock; the atomic write
    keeps CLAUDE.md torn-free regardless. (Same single-writer/atomic/dedupe
    discipline as the marketplace lock + atomic rules-install.)
- **Two opt-in commands (default OFF), mirroring `/janitor-auto-manage-oauth-on|off`:**
  - **`/janitor-auto-repomap-on`** — set the opt-in flag AND insert the fenced
    block (seeded with the current map) after any human front-matter. Idempotent.
  - **`/janitor-auto-repomap-off`** — clear the flag AND **remove the fenced
    block entirely** (splice out everything between START/END fences inclusive),
    restoring CLAUDE.md to its no-map state. The human narrative is untouched.
  Both preserve all text outside the fences; both are a single grep+splice on the
  unique fence strings (no markdown parsing). While OFF, the detector no-ops.

## 4. Safety / boundaries

- **Opt-in, default OFF** — enabled only by `/janitor-auto-repomap-on`, disabled
  (and the block removed) by `/janitor-auto-repomap-off`. Auto-editing CLAUDE.md
  is invasive AND expensive (§5); never surprise a user.
- **Only ever rewrite between the fences.** Fences absent → do nothing until
  `/janitor-auto-repomap-on` inserts them. Fences malformed/duplicated → bail +
  emit a drift warning, never guess.
- **Atomic write** (the rules_installer lesson) — never a torn CLAUDE.md.
- **Respect .gitignore + skip** vendored/generated/build dirs, `*_dev/`,
  `reports/`, `node_modules`, etc. (reuse the existing scan-exclusion list).
- **Bounded size:** cap the map (e.g. ≤ N lines); above the cap, deepen
  convention-collapse rather than spilling. A map that's as big as the code
  defeats the purpose.
- **Cross-project:** runs only in the project the janitor was armed in
  (project-scoped, like every other detector — NOT a daemon/global op).

## 5. Economics — read-value vs WRITE (cache) cost — the write cost DOMINATES

**Read value (why the map exists):** a map ≤ ~1–2 % of the codebase's token count
that answers ≥ 80 % of "what does this file/symbol do" without opening the file.
Break-even after a handful of lookups.

**Write cost (the dominant constraint — drives the whole trigger strategy):**
CLAUDE.md sits in the **cached prompt prefix**. Editing it busts the cache →
the ENTIRE context is re-processed at full (uncached) input price on the next
turn, AND every forked subagent re-pays it. At ~1M context a single careless
edit can burn a **whole 5-hour token budget**. So keeping the map *perfectly
fresh* is the wrong goal; **minimizing and timing the writes** is the goal. A
slightly-stale map costs ~nothing; an eagerly-written one can cost everything.

**Cost model:** `write_cost ≈ current_context_tokens × (1 − cache_hit_fraction)
× fanout(active_subagents)`. Minimize by writing when context is **small** AND
**no subagents** are active — and, ideally, when a cache reset is *already
happening*.

**The key lever — ride the compaction.** Compaction already rewrites/invalidates
the context cache. Writing the map in the **PostCompact** window piggybacks on an
already-paid reset → **marginal cost ≈ 0.** This is the PRIMARY write window.

**Scheduling policy (this is the gate referenced by §3 step 3):**
- **PREFER (open the gate):** just compacted (PostCompact/SessionStart:compact
  hook) **OR** context low (< ~150–200k) **OR** no subagents have run for a
  while → if `map-dirty`, write now.
- **AVOID (keep gate shut):** context high (~600–800k+) → **defer even a large
  change**; a compaction is near — wait for that free window.
- **FORCE sooner** only when Δ > ~20–30 % of repo **AND** context is not high;
  if context is high, still wait for the imminent compaction.
- **OFF** → never write.

**Signals (open question — see R7):** the **PostCompact / SessionStart:compact
hook is the reliable "cache just reset" signal** and is the backbone of the
policy. Whether a detector/hook can read the **current context %** and
**subagent-active** state directly needs investigation; if not exposed, fall
back to heuristics (time-since-last-compaction, recent tool-activity bursts).

**Acceptance for this section:** the maintainer must NEVER write CLAUDE.md while
context is high for a small change, and SHOULD land ~all writes in a
post-compaction / low-context window (measure: fraction of map writes that occur
within N turns of a compaction → target high).

## 9. Acceptance criteria

- AC1. For this repo, the generated map ≤ ~2 % of the codebase token count and
  covers every file (collapsed where uniform).
- AC2. Re-running with no code change makes ZERO edits (hash match).
- AC3. A single-function edit produces a localized map diff.
- AC4. The maintainer never touches a byte outside the markers (verified by
  diffing the non-fenced regions).
- AC5. Atomic — no torn CLAUDE.md, no temp residue, malformed markers → safe bail.
- AC6. Works on py/ts/go/rust; opt-in; project-scoped.
- AC7. **OFF by default;** `/janitor-auto-repomap-on` inserts the fenced block,
  `/janitor-auto-repomap-off` removes it entirely — both leave every non-fenced
  byte identical.
- AC8. **Cache discipline (§5):** never writes CLAUDE.md while context is high
  for a small change; ~all writes land in a post-compaction / low-context window.
- AC9. **Error-prevention bar (THE quality test, not coverage):** the generated
  map would have PREVENTED the daemon.py:345 mistake — its `Task.run()` line
  makes the *unconditional* (finally) last-run stamp explicit, so a reader cannot
  conclude "stale last-run = failing refresh." Generalized: the map answers the
  §7 litmus corpus correctly. A map that's complete but shallow FAILS this AC.
