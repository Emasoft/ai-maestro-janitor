PREREQUISITE to TRDD-A70YJLXN's box 2, not part of it.

TRDD-A70YJLXN measures the publish-to-installed latency of a plugin release (box 2). To attribute an install to an actor, the janitor's own log lines for the release window must survive. On this host they do not, so the 2026-10-07 v3.8.11 investigation ended with the mechanism UNESTABLISHED: the janitor's own auto-update path was neither excluded nor implicated, because its log sink for that night is not retained.

TWO SINKS, TWO FIXES — but only one sink is diagnosed, and the other is an open question (see the 2026-10-20 05:50 entry in the Approval log).

(1) The per-project logs — THE SWEEP'S OWN FACTS, WHICH THE CORRECTION BELOW SETS ASIDE FOR THIS SINK: scripts/dispatch.py's _phase_log_retention prunes .janitor/logs/ files older than CLAUDE_PLUGIN_OPTION_LOG_RETENTION_DAYS (default 30) and .janitor/state/ files older than CLAUDE_PLUGIN_OPTION_STATE_RETENTION_DAYS (default 45). CORRECTION — SINK (1) WAS MISDIAGNOSED, by a path distinction this card's first draft got wrong. The sweep does NOT reach the files it named: _sweep_old_files(state.log_dir(), ...) and state.state_dir() resolve under janitor_root() = project_root() / '.janitor', the PROJECT tree, while the plugin's own .janitor/logs/version-update.log and .janitor/state/last-run-version-update.ts live under the PLUGIN DATA dir, a different tree. So the 30-day and 45-day sweeps never touched them and no retention window binds them. What truncates them is something else this card has not identified. The measured evidence points at it: version-update.log spans 2026-09-13 11:55 to 16:00, about four hours, not thirty days, and a 30-day sweep would have left a 30-day span — so the cause is not a sweep. THIS SINK WAS THEN RESOLVED, and the resolution is the most consequential fact in the card's whole investigation: the four-hour file above is the PLUGIN DATA dir's copy, and the LIVE sink is the PROJECT tree's .janitor/logs/version-update.log — a DIFFERENT file, 186 KB with a 1 MiB .log.1 sibling, which SURVIVES and covers the 2026-10-07 install minute. The 04:20 and 05:00 entries of TRDD-A70YJLXN declared the janitor's own log unrecoverable after examining the plugin DATA copy and concluding about the project copy — a file's absence asserted from where it was LOOKED rather than from where it is WRITTEN. The project-tree file settles TRDD-A70YJLXN's box 2 attribution: its last fire before the 23:02:13 local publish was 23:01:24 (49 s early, observing 3.8.10) and the next was 23:11:14 (6m53s after the 23:04:21 install), so no detector fire landed inside the 128-second window and the janitor's own path is EXCLUDED by its trigger schedule. The consequence for THIS card: the sink it was written to fix is not an unknown — it is a file that survives, and the file the card proposed to create ALREADY EXISTS and already receives the detector's lines, because the detector logs under the actor 'version-update' (scripts/detectors/version-update.py:118) while the DAEMON's chore logs under the actor 'daemon' (scripts/daemon.py:723, 753, 756) into the flooded daemon.log. So the remaining work is NOT one item but THREE, and the correction that resolved the open question ALSO restored the retention problem it had dropped. (a) THE ACTOR CHANGE for the daemon-side lines — the daemon chore logs under the actor 'daemon' (scripts/daemon.py:723, 753, 756) into the flooded daemon.log, while the detector logs under 'version-update' (scripts/detectors/version-update.py:118) into its own file. Changing the daemon-side actor routes those lines out of the flood. (b) A RETENTION FLOOR FOR THE PROJECT TREE'S PER-CHORE LOGS, and this is the item with the evidentiary weight, and the correction had thrown it away. The sweep's target is _sweep_old_files(state.log_dir(), ...) at scripts/dispatch.py:1539, and JANITOR_LOG_DIR is NOT set in dispatch.py (the daemon sets it; dispatch does not), so state.log_dir() resolves to project_root()/.janitor/logs — the PROJECT tree, which is where the file that settled TRDD-A70YJLXN lives. The plugin DATA dir's copy is the one the sweep never reaches, and the evidence bears it out: that copy has survived 37 days untouched by any sweep, while the project tree's file is the sweep's designated target. So the sweep DOES bound the file that matters, and the 2026-10-07 case was recovered TWELVE DAYS after the event against a THIRTY-DAY budget: a twelve-day margin, and an investigation that had come forty days later would have lost the file and the exclusion with it. The floor must be sized against the EVENT-TO-INVESTIGATION interval, not the release window. (c) THE DAEMON-SIDE RECORDS needed to close the residual candidates, which is the same actor change seen from the other side: TRDD-A70YJLXN narrowed that night's trigger set to three candidates, of which the janitor's detector-triggered path is EXCLUDED on its retained log, and the janitor's 6 h daemon chore and the server's 4 h absorbed beat are NEITHER EXCLUDED NOR TESTABLE — their records for that night are not retained. The card's justification is now precisely the exclusions it cannot make.

(2) The machine-wide daemon log: scripts/daemon.py writes the version-update chore's lines to daemon.log in the plugin DATA global-state dir, and state.rotate_log_if_big rotates it by SIZE (1 MiB) to daemon.log.1, keeping exactly one previous generation. Measured on this host: daemon.log covered 2026-10-19 10:46:26 onward and daemon.log.1 covered 2026-10-18 12:34 to 2026-10-19 10:46. The version-update chore is not the only writer - the daemon logs every tick, so the file turns over quickly, and the 2026-10-07 night is long gone. The size-based rotation is the reason, and it is in THIS repo's code. TWO CORRECTIONS TO THIS PARAGRAPH, both from the review of fb1585be. First, the RETAINED WINDOW is what the numbers say, and they say about a DAY, not hours: daemon.log plus daemon.log.1 together cover 2026-10-18 12:34 to 2026-10-19 10:46, about 22 hours, and everything older is gone. Second, and more important for the fix: a size-based rotation at a FIXED byte threshold is NOT a configurable retention span at all - the window it retains depends on the write rate, and shrinks on a busier host. So 'raise the retention' does not apply to this sink: there is no knob for it. The only levers are the byte threshold and the number of generations kept.

WHY THIS IS A PREREQUISITE AND NOT A NICE-TO-HAVE: a future release that is installed while the janitor's own log sink has already turned over produces exactly the same unresolvable investigation. The observation needs the sink to span the release-to-install window, which means the retention must exceed the time between a publish and the observation of its install.

PREFERRED FIX (the review of fb1585be was right that this card led with the expensive option and never named the cheap one). THE PREFERRED FIX IS A DEDICATED, LOW-VOLUME LOG FOR THE VERSION-UPDATE CHORE, not a bigger daemon log. The daemon log is flooded: it records every tick, and the version-update chore's lines are a tiny fraction of it. Enlarging a flooded sink to preserve a handful of lines is the expensive way to solve it, and it costs every host disk. A separate file that only the version-update chore writes would survive the ordinary retention untouched, at negligible cost, and it is the direct answer to what A70YJLXN's investigation actually needed - the janitor's own auto-update lines for a given release window. The repo already has the precedent: per-chore logs exist for memory-guard and cold-cache-clear, and the version-update chore currently writes to the daemon-wide sink via state.log_line('daemon', ...). Splitting it out is the change. The alternatives, in order of cost: (a) a dedicated low-volume log (preferred, negligible cost, no change to daemon.log's size or generation count); (b) raising the byte threshold and keeping more generations of daemon.log (works, costs disk on every host, and the window stays rate-dependent); (c) reducing the daemon's per-tick logging (a much larger change, outside this card's scope). This card should implement (a), and only fall back to (b) if (a) is refused.

ACCEPTANCE: the daemon log sink retains a window that provably covers a publish-to-install interval (the two retention knobs and the rotation generation count are each adequate for the window), and the janitor's version-update log lines for a given release window are still on disk after that window has elapsed. THE CADENCE BOUND, which the 06:35 entry of TRDD-A70YJLXN moved here and this card had not yet received. The unsound 'roughly 128/300 of the detector's cycles' figure is WITHDRAWN: the detector's schedule is SESSION-ANCHORED, not a uniform 300 s grid (it fires only while a session is live and resumes promptly at session start), so that fraction was never a probability. THE SOUND NUMBER IS THE PUBLISH-TO-INSTALL INTERVAL THE MECHANISM MUST BEAT: 128 s on 2026-10-07. The effective window is NARROWER than that, because a 'claude plugin update' invocation plausibly takes tens of seconds and the daemon's consume-on-next-loop adds latency on top, so a detector fire inside the window would still have had to COMPLETE the update before the install. So the requirement is: the trigger-to-install-COMPLETION latency must be shorter than the publish-to-install interval — 128 s on the observed release, and shorter in practice — and the mechanism must be able to record whether the trigger fired at all. A retained log answers 'did the chore act?' ONLY if the chore could have fired and COMPLETED inside the event window; retention alone is necessary and not sufficient. The acceptance must therefore be verified against a stated trigger-to-install-completion bound, not only against a stated retention window.

THE GATE HAS A DETERMINISTIC PROXY AND A SLOW REAL-WORLD CONFIRMATION, and the first is what the card is actually verified against. The DETERMINISTIC PROXY: a test that asserts (i) the version-update chore's lines land in the dedicated log and NOT only in the daemon-wide sink, and (ii) that the dedicated log's retention covers a stated window - that the file survives a simulated age of the required window. The SLOW CONFIRMATION: release a version, let the observation window elapse, and read the janitor's own auto-update lines for that release. The card previously claimed the slow one was 'Measurable' while never naming an owner for the release or a threshold for the passing state, and it is weeks long - so it is recorded here as a confirmation, not as the gate.

CAREFUL: increasing the daemon log retention raises disk use on every machine with the plugin installed, and keeping more than one rotation generation multiplies that. The knob values are the user's configuration (CLAUDE_PLUGIN_OPTION_LOG_RETENTION_DAYS, CLAUDE_PLUGIN_OPTION_STATE_RETENTION_DAYS) as much as the code's, so the fix may be a documented recommendation rather than a default change - the user owns the choice, and this card must not silently change the default for every host. BUT THE TWO KNOBS HAVE DIFFERENT OWNERS AND DIFFERENT BLAST RADIOS, and the caution above treated them as one. CLAUDE_PLUGIN_OPTION_LOG_RETENTION_DAYS and CLAUDE_PLUGIN_OPTION_STATE_RETENTION_DAYS are read per PROJECT (the sweep runs in the project tree), so they are the user's per-installation configuration and raising them affects one project. The daemon log is MACHINE-WIDE and lives in the plugin DATA global-state dir, so its threshold and generation count are a DEFAULT IN THE CODE and a change to them lands for every host that has the plugin installed. So recommending the user raise a knob does nothing for the daemon log at all - there is no knob for that sink - and a code change to it is a fleet-wide change, which is exactly why the preferred fix above is the one that touches no fleet-wide default: a dedicated low-volume log, at negligible cost, changing nothing anyone else depends on.
