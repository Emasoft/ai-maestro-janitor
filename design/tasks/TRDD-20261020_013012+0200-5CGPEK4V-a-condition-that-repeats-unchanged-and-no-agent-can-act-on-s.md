# A condition that repeats unchanged and no agent can act on should escalate once and stay quiet

THE OWNER'S ASK, verbatim, 2026-10-20: "you must find a way to avoid/prevent such things to happen. think a more intelligent solution." The subject of "such things" was a janitor alert that repeats on every heartbeat fire and that no agent can act on.

WHY THE RELEASE IS NOT THE ANSWER. The fix for the specific instance (the owner-only rotator condition re-raising itself every 5 minutes) is already written and is recorded on TRDD-PWL9GD4E, which is about the unreleased 599 commits. But shipping it is a one-shot unblock of an incident that has already happened. It changes the layer where the repetition occurs for ROTATOR conditions only: the repo's build does exclude the owner-only rotator conditions from agent context, so the NEXT owner-only rotator condition does not repeat the same way. What the repo does NOT do — in either build — is count repetition GENERALLY, for any condition, by any detector. So the next detector with the same shape, outside the rotator module, repeats the same way today. This card is that general half: the prevention layer, and the part of the owner's ask that outlives the incident.

THE MECHANISM, stated plainly. Every heartbeat fire runs the detectors, collects their stdout lines, and hands them to a model turn. Of the 47 AGENT-VISIBLE detectors (the census below measures the other 31 out of the 78 as advisory or control-plane-only, neither of which reaches a model turn), a line is printed on EVERY fire whenever its underlying condition holds, regardless of whether anything changed since the last fire, and regardless of whether the reader can act on it. So a STANDING condition — one that persists for days — produces a fresh actionable-looking line every fire. The two properties that make it noise rather than signal are: (a) the condition is unchanged since last time, and (b) no agent can resolve it, because it needs the owner (a credential, a commercial decision, a physical action).

THE DESIGN, in the terms the janitor already has. The findings ledger (scripts/lib/findings_ledger.py) already records every dropped advisory with a severity, and already has a pull model with a cursor and a surfaced-to-human marker. The rotator alert module (scripts/lib/rotator_alert.py) already splits URGENT from ADVISORY and already dedupes advisories by a signature digest against a per-project stamp. What neither does is count REPETITION of an un-actionable condition. The mechanism to add: for a condition that (1) has fired on N consecutive fires with an UNCHANGED signature, and (2) is classified owner-only, emit it ONCE as a fresh line, then thereafter emit at most one line carrying a COUNT and a pointer to the ledger entry ("still waiting on the owner: N fires since <time>"), and then stay silent until the signature changes or the condition clears. The first occurrence is the loud one; repetition is not urgency, it is the opposite.

WHY THE CLASSIFICATION MUST EXIST FIRST, or the mechanism cannot be built. "No agent can act on it" is not currently a property anything in the code records. The repo's rotator_alert module has _AGENT_VISIBLE_CONDITIONS = frozenset({"tick-stalled"}) and an advisory predicate (_is_advisory) that covers spare-stale and capture-refused:*; the general detector path has no equivalent, and the quiet filter treats every dropped advisory line alike (sev="LOW"). So the agent-actionable vs owner-only distinction is currently a property of a handful of rotator conditions, not a general capability. A general repetition-escalation needs that classification to be general, and a general classification is a bigger change than the escalation itself. The honest scoping: this card is the escalation MECHANISM, and it depends on a classification that must be landed first or together with it. THE POPULATION IS CENSUSED IN PART, and the rest is TRDD-F3LVCQ39, which this card is now blocked by. Measured: 78 detectors are registered (dispatch.py:83), in three classes the code does implement — 29 ADVISORY (dropped by the quiet filter into the findings ledger at sev=LOW, so they never reach a model turn), 2 CONTROL-PLANE-ONLY (token-usage-anomaly, window-burn-rate; their output goes to a control log and no agent text is returned), and 47 AGENT-VISIBLE (printed on every fire the condition holds, and read by a model turn). NONE of those three classes says whether an AGENT CAN ACT ON THE CONDITION, and that is the classification this mechanism needs. The census card records the sample that shows the gap is real and not merely absent: ticket-dispatch prints "NEEDS A HUMAN" and "await YOUR approval" in its own line text, oauth-login-needed prints "need a one-time login", remote-credentials prints "URGENT: ... embeds a secret" — the words are in the prose and the classification is not in the data, so nothing mechanical can act on them. The census's remaining work is to classify each of the 47 agent-visible detectors' CONDITIONS as AGENT-ACTIONABLE / OWNER-ONLY / UNCLASSIFIED, and to record that classification AS DATA the dispatcher can read. Until that lands, this card's design cannot be written against real numbers.

WHAT IS MEASURED, on this host, for the shape of the problem. Over 3,610 heartbeat turns in this project's token-meter.jsonl, 20 turns exceeded 2M weighted tokens and four exceeded 7M, the largest at 14,396,446 (2026-10-08 16:42, 66 assistant messages in one turn). The heavy tail is the ordinary shape of a long agent session, so the cost of a repeated drift line is not primarily tokens. The reasoning this card rests on is a mechanism, not a measurement: a standing condition re-raised on every fire trains the model to read the channel as noise, and a channel the model has learned to discount is exactly the one where a genuinely urgent line gets missed. That is an argument for the mechanism, and it is the argument a reviewer should weigh — the card does NOT claim a measured attention cost, because no measurement of one exists here.

THE BOUNDARY THIS MUST NOT CROSS. Escalation is for conditions no agent can act on. A condition an agent CAN act on must keep printing every fire until it is acted on, because silence would hide a live problem. The existing urgent/advisory split (commit f795816c, TRDD-JWIGGMH0) already encodes most of this distinction for rotator conditions; this card generalises the REPETITION half of it, it does not replace it. It must also not suppress anything at HIGH or CRITICAL severity (findings_ledger.NEVER_SUPPRESSED_SEVERITIES already refuses to let .janitor.toml silence those) and it must not lose a finding: the ledger entry and its count must remain queryable, so a standing owner chore is still visible in /janitor-findings and to the owner, even when it is no longer re-raised at the agent.

ACCEPTANCE. (1) An owner-only condition that fires unchanged N times emits a fresh line on the first fire and a counted line thereafter, and then goes silent — asserted by a test that drives the dispatcher with the same condition over N fires and counts the emitted lines. (2) A condition that CHANGES (its signature differs) re-emits a fresh line, so a real change is never swallowed. (3) An agent-actionable condition still prints on every fire until it clears. (4) The count and the ledger entry are readable afterwards: nothing is deleted, only de-duplicated from the agent's context. (5) A HIGH/CRITICAL finding is never suppressed by this mechanism. (6) The classification of owner-only is stated for each condition the mechanism governs, and a condition with no classification is treated as agent-actionable (fail OPEN toward visibility, never toward silence).

NEXT ACTION: this card is blocked by TRDD-F3LVCQ39 (the census), and it unblocks when that card's table is complete. The census's own next action is the mechanical part: classify the 47 agent-visible detectors' conditions, reading each detector's condition text and the state it fires on, and record the result. That is a bounded, per-file job a worker can do in batches. When the table is complete, this card's design is written against real numbers, and the "THE POPULATION IS CENSUSED IN PART" paragraph above is replaced by the census's counts. THE MEASURED REPETITION is already in hand and does not depend on the census: the two live conditions' first_seen are 2026-10-18 14:18 and 2026-10-19 16:00, and this project's heartbeat-fires.log records 103 fires in the 34.8 h since the first of them — 2.96 fires/h, about 71 identical drift lines a day observed, against a 288/day ceiling the 5-minute cadence would allow.
