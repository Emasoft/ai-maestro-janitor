## THE DESIGN CONSULT RETURNED — the root-walking proposal is REFUTED on macOS, and the mechanism is CLAUDE_PID, not tree-walking

THE DESIGN CONSULT RETURNED, AND IT REFUTES THIS CARD'S OWN PROPOSAL. The full memo is `docs_dev/advisor-abandonment-polarity.md` (ADVISOR, 2026-10-20, 558 lines, all figures measured on this host). The proposal this card carried — 'identify the CLAUDE-FAMILY ROOT of the chain and require that root to be GONE' — MUST NOT BE IMPLEMENTED, and it is refuted on the platform, not on taste.
ON macOS THE ROOT OF EVERY LONG-LIVED PROCESS TREE IS `launchd` (pid 1), and a process whose Claude session died is REPARENTED TO pid 1 — that is exactly what makes it an orphan. So 'walk to the root, is the root a Claude-family root?' answers 'no' for precisely the processes the feature exists to kill, and 'yes' only for processes still inside a LIVE session, which must not be killed. The rule would INVERT: select live work, refuse orphans. The proposal's own escape hatch ('an UNRECOGNISED root is UNKNOWN and must REFUSE') makes it worse: the root is essentially always launchd, i.e. unrecognised, i.e. REFUSE — a rule that refuses everything, which reads as prudent in review and is inert in production. The advisor names this the single most dangerous pitfall of the whole design, and the reason it is hard to see is that the feature is DEFAULT-OFF, so the inertness would surface only at the moment the host actually needs it.
THE MECHANISM THAT WORKS IS `CLAUDE_PID`, AND IT IS ALREADY IN THE ENVIRONMENT. MEASURED on this host in ONE `ps eww -axo pid=,command=` read, and RE-MEASURED on 2026-10-20 23:20 because the earlier figure did not reconcile with a second figure elsewhere in this card: the SET of owner pids is STABLE, but the COUNT of processes carrying a pointer is NOT — consecutive reads minutes apart returned 68, 74 and 94 processes carrying `CLAUDE_PID`, over the SAME 10 distinct owner values. The remaining TWO are not live sessions: 20716 is DEAD, and its descendants are still running — that is the orphan case — while the eleventh value is the literal token `CLAUDE_PID={v}` with a pid of `{v}`, which is a template artefact, not a pointer, and MUST NOT be treated as one. The card's earlier '48 processes / 10 distinct values' pair (in the design memo) and the '156' figure quoted here were BOTH taken from reads whose populations differed, and they did not reconcile with each other; the re-measurement above replaced both with the stable facts, and the counts are now stated as what they are — per-snapshot readings that vary with the host's activity. `CLAUDE_PID` is a positive pointer from a descendant to the owning session, it SURVIVES REPARENTING (the case the ancestry channel is blind to), and owner-liveness is a single existence check against the live OS. Abandonment therefore becomes 'the owner pointer is positively identified AND its target is DEAD' — never 'no claude ancestor'. THE OWNER-PID CHECK MUST DISTINGUISH THREE CASES, NOT TWO, OR A RECYCLED PID SILENTLY FREEZES THE GUARD: (a) the owner pid is ABSENT from the process table entirely => the owner is DEAD => abandoned; (b) the owner pid is PRESENT and its name is a Claude-family name => the owner is ALIVE => not abandoned, refuse; (c) the owner pid is PRESENT but its name is NOT a Claude-family name => the pid was RECYCLED and the real owner is gone, but the pointer can no longer prove it => UNKNOWN => REFUSE. Case (c) is the failure mode a two-way check misses: a liveness test alone sees 'pid exists' and concludes the session is alive, so the orphan is refused forever and the guard reads as inert — the exact symptom this card has been fighting. MEASURED on this host: `kern.maxproc` is 16000, so pids ARE recycled, and MEASURED pid 20716 (the dead owner of the four real orphans) is absent ENTIRELY from the process table (`ps -p 20716` exits 1), so today it is case (a); the rule must still handle (c) correctly.
