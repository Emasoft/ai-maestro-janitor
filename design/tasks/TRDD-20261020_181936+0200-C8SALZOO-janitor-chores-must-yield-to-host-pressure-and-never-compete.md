# Janitor chores must yield to host pressure and never compete for CPU

OWNER DIRECTIVE (2026-10-20), verbatim: 'make this rule for the janitor chores: never execute them when the system is under pressure. wait a moment when the system activity is low to launch them, and pause them as soon as the system becomes too busy again. even if they will slip to the night, it is better than having those chores executed while the other main agents are struggling for cpu time and resources!'

THE INCIDENT THAT PROMPTED IT, MEASURED. On 2026-10-20 the host was unresponsive: load average 856 on a 14-core box, 427 runnable processes, memory 73% free and zero swap. The 166 iOS Simulator daemons were the largest runnable class, but the janitor's OWN background work was competing for the same CPU while seven other Claude sessions were struggling: 43 agentlenspro statusline processes alive at once during a fan-out, four concurrent pytest runs of the janitor's own test suite, six orphaned peak-space/watch.mjs processes reparented to launchd and still burning CPU two hours after their session ended, and tsc --noEmit runs from four different projects. The janitor's chores were not the dominant cause - they were a CONTRIBUTORY cause, and a contributor is still a cause.

THE RULE, in one sentence: a janitor chore must not start while the host is under pressure, and must yield the moment pressure appears.

WHAT 'UNDER PRESSURE' MEANS, and the existing machinery to build on. The janitor already has a load probe: scripts/detectors/host-load.py reads the load average and compares it to a bar of cores x 4 (56 on this host), and scripts/daemon.py's task_memory_guard already reads free memory with a floor. The pressure signal for this rule is the CPU one, because the measured incident was a CPU storm with memory to spare - a free-memory-only probe would have read the host as HEALTHY while it was unusable. The bar must be the LOAD AVERAGE relative to the core count, because an absolute bar does not travel between a 4-core and a 64-core host.

THE THREE BEHAVIOURS, and they are different mechanisms, not one. (1) DEFER: a chore whose due time arrives while the host is under pressure does NOT run; it is rescheduled and runs at the next beat at which the host is calm. A chore that is a few hours late is BETTER than a chore that starves the agent sessions, per the owner's directive. (2) PAUSE: a chore ALREADY RUNNING when pressure appears must be interruptible, so a long-running chore (the daemon's version-update sweep, the oauth rotator's browser capture, a memory chore) yields rather than finishing its work into a saturated host. (3) YIELD THE CPU: the janitor's own daemon and detectors must not themselves be the load. The statusline churn (43 processes) and the abandoned pytest runs are janitor-adjacent work that outlived its session, and a rule that only defers the NEXT beat leaves those running.

THE HARD PART, AND THE CARD MUST SAY IT PLAINLY: A RUNAWAY-KILL DAEMON IS THE ONE CHORE THAT CANNOT WAIT. TRDD-5G66S0HK's whole purpose is to relieve pressure, and a pressure-aware scheduler that defers the pressure-relief chore when the host is under pressure is a deadlock: the one chore that must always run is the one a busy host would suppress. The resolution this card must implement: the pressure gate applies to the MAINTENANCE chores, and the runaway-kill chore is EXEMPT - it runs regardless, because it is the mechanism that ENDS the pressure. A card that does not carve that exemption out ships a janitor that starves exactly when it is needed.

INTERACTION WITH THE EXISTING CHORE ARCHITECTURE, and where this lands. The daemon's chores are registered in scripts/daemon.py's Task registry and mirrored name-for-name in scripts/lib/harness_backend.py's GLOBAL_CHORES (tests/test_harness_backend.py asserts the two match, so a new chore needs an entry in BOTH). The per-project DETECTORS run under scripts/dispatch.py's heartbeat, which is a different path from the daemon's chores and has its own cadence. The gate therefore needs a home in each path, or the rule is only half-enforced.

WHAT MUST BE MEASURED BEFORE THE GATE SHIPS, because a threshold guessed under pressure is how a bad rule gets made. (a) The load-average bar that actually corresponds to 'the other main agents are struggling'. Measured on this host: at load 856 with 427 runnable processes the box was unusable; at load 214 (after the simulator and orphan cleanup) it was usable again. The bar must sit in that band and must not be so low that a single normal fan-out trips it, nor so high that the host is already dead when the gate closes. (b) How a chore learns the pressure signal CHEAPLY: a load average read is one syscall-class call, and the daemon already has a load probe; the gate must not add a per-chore probe that costs a subprocess spawn each. (c) How the load average behaves on THIS host under normal work, because a 14-core box running seven Claude sessions may sit at a load of 100+ without anyone struggling - if so, the bar must be relative to something other than the core count, and the card must MEASURE that rather than assume it.

ACCEPTANCE: (1) a janitor chore's due beat is DEFERRED, not run, when the host is over the pressure bar, and it runs at the next calm beat - with a test that asserts the deferral and one that asserts the eventual run; (2) a chore already running when pressure appears is interrupted or yields, with a test; (3) the runaway-kill chore is EXEMPT from the gate, with a test that asserts it RUNS under simulated pressure - this is the anti-deadlock acceptance and it is the most important one; (4) the pressure bar is derived from the host's core count and is a documented, MEASURED function of it, not a constant; (5) the gate applies in BOTH paths - the daemon's Task registry and the per-project heartbeat detectors - or the card states explicitly which path it covers and why the other is exempt; (6) a status line reports a deferred chore, so a chore that slips to the night is VISIBLE and not silently starved; (7) the janitor's own abandoned work (the statusline churn, the orphaned watchers) is reaped by a mechanism of its own, because deferring the next beat does nothing for work already running.

DO NOT make the bar a load-average constant copied from another host. MEASURE this host's band first and record the numbers with their scope.

## Measurements

2026-10-20 20:20 — THE LOAD BAR IS MEASURED, and the card's precondition is FALSIFIED as stated: the existing bar (cores x 4 = 56) is NOT a 'struggling' bar on this host, it is a bar this host crosses CONSTANTLY while being perfectly usable. MEASURED over six samples two minutes apart: load5 = 192.49, 193.06, 192.47, 192.76, 189.44, 185.21 (14 cores, so 13.2x to 13.8x cores) with runnable = 159, 118, 169, 128, 132, 132 and total RSS 35-37 GB on a 64 GB box. THE HOST IS USABLE at load ~190 — nine Claude sessions are running fine, tool calls are fast, and the swapfile sits at its normal 82% of its own total with 1M free pages. So the card's premise that 'the bar must sit in the band between 214 (usable) and 856 (unusable)' is WRONG: 214 and 190 are the SAME condition, and both are usable. What actually differed in the incident was not the load average but the RUNNABLE COUNT: 427 runnable at the incident, versus 118-169 now. A load average on macOS counts UNINTERRUPTIBLE-SLEEP processes too, and this host's baseline includes a large population of them (the 166 iOS Simulator daemons and their launchd agents), so the load average is inflated by a roughly CONSTANT background and does not track 'are the agents struggling'. A bar on the load average would therefore have the janitor deferring its chores forever on a healthy busy host. THE BAR MUST BE ON A SIGNAL THAT MOVES WITH THE STALL. The candidate is the RUNNABLE COUNT (processes actually runnable right now), because that is what the incident moved (427 vs ~130) and because it is directly the quantity the user feels as 'the other main agents are struggling for CPU time'. MEASURED SPREAD: 118-169 runnable across six samples on a HEALTHY busy host, so a bar around 300 runnable separates the measured healthy band from the measured 427 incident with real headroom on both sides, and it is measured on THIS host with its scope recorded. The bar is therefore NOT a function of the core count and MUST NOT be presented as one — the card's acceptance clause 4 ('the pressure bar is derived from the host's core count') is REFUTED by this measurement and needs its correction, because a core-relative bar has no meaning for a count that is not a rate. A SECOND FINDING FOR THE SAME CARD: scripts/detectors/host-load.py has NEVER fired on this host — there is no host-load.log in this project's .janitor/logs/ nor in the plugin DATA global-state dir — because the load average here (13.2x-13.8x cores) sits permanently above the cores x 4 bar, so the detector's 'first fire of an overload episode' never had a normal state to depart from. Any pressure rule built on that bar would be permanently-on, and the card's requirement (6) that a deferred chore be VISIBLE would be drowned by a detector that fires on every beat.

## The review verdict — the gate's architecture survives, the kill-ledger destination does not

2026-10-20 23:40 — AN ADVERSARIAL REVIEW of the first implementation returned "do not land as-is". I CHECKED its findings against the tree before acting on any of them (my own read of the cited code, on the uncommitted working tree of 2026-10-20 23:07, plus an AST parse of the detector roster). The verdict was split, and the split is the finding: the pressure gate's ARCHITECTURE survives, and SEVEN defects in it are confirmed and are being fixed; the KILL-LEDGER DESTINATION (TRDD-ZIKYQQY0 A-2) is a NO-OP BY CONSTRUCTION and is pulled out of this card's scope. "No-op in production" would be a claim about observed behaviour on a path that has never run: the runaway-kill chore is DEFAULT-OFF (`CLAUDE_PLUGIN_OPTION_RUNAWAY_GUARD_ENABLED` is set nowhere on this host), so no kill has EVER happened here. The accurate claim is about the SOURCE ORDER — the read happens after the kill, so it cannot return a usable value — which is a statement about the code's structure and does not need a production observation. The ten findings below are TWO SETS, and the split matters: findings (1)-(3) are about A-2, findings (4)-(10) are about the gate. Neither set has seven or three the other way round. CONFIRMED FINDINGS — each DEFECT verified by me; the FIX named in each is a proposal, not a landed change: (1) A-2 reads the killed process's OWN environment AFTER the process was killed — `kill_process` is at scripts/daemon.py:1281 and the ledger record comes after it — so the read returns None in the normal case (the pid is gone from the process table) and cannot return a usable value in the zombie case (an unreaped zombie with an empty argv). The feature could not work in production, and its test MOCKED the exact step that fails. (2) The rationale's "the entry is never LOST" was FALSE: findings_ledger.record swallows its own write failure (`except Exception: pass`, findings_ledger.py:329), so pointing the record at a project directory the janitor cannot write loses the entry entirely. The pre-A-2 shape (the janitor's own ledger) is the MORE RELIABLE target — not a lossless one, because the same swallowed failure applies to it — so the A-2 shape added a second, likelier way to lose the entry rather than removing one. (3) `CLAUDE_PROJECT_DIR` comes from the environment of the process being killed, so the change let a to-be-killed process CHOOSE where the janitor writes. The severity fact sharpens this rather than softening it: the entry is HIGH, and HIGH is in NEVER_SUPPRESSED_SEVERITIES, so the chosen directory could not silence it. THE HARM, named precisely, because the severity fact does not soften it: the foreign process gets to place a DURABLE, UNQUIETABLE HIGH entry in ANOTHER PROJECT'S LEDGER — it cannot be suppressed by that project's own `.janitor.toml`, so the pollution is permanent for that project. The write primitive is the defect, and the severity fact is what makes the primitive unrecoverable rather than a nuisance. (4) The detector-path gate logged one line per detector per fire, with no episode discipline, and evaluated the gate BEFORE the detector's own due-check — so it logged a deferral for a detector that was not going to run anyway. That is a MISLEADING line rather than a false claim, and a reader of the log has to tell the two apart. (5) A test read the LIVE host's runnable count and then asserted the chores had run, so it failed whenever the host was busy — the exact condition the feature exists for. The fix is to make the test HERMETIC (inject the reading) while the production behaviour stays host-dependent; the test's host-dependence is not itself the defect. (6) The episode latch cleared on any calm reading, so a host hovering at 299/300 re-announced on every beat — a HYSTERESIS bug. (7) Separately, the latch-clearing function's docstring described a per-chore behaviour its code did not implement — a COMMENT THAT LIES, a different class of defect from (6) and fixed by a different change. (8) Nothing stopped a backlog from all firing at once on the first calm beat — a thundering herd the directive did not ask for. (9) The directive's "pause them as soon as the system becomes too busy again" half is NOT implemented: the gate governs LAUNCH, not INTERRUPTION. The rework is DIRECTED to state that gap in the code rather than leave it implicit (ITEM 10 of the rework spec) — it is NOT stated in the code today, and a fix that does not say it leaves the gap implicit. (10) A mis-set BAR is invisible: fail-open covers an unreadable reading, but a bar below the host's healthy baseline starves every chore with one log line per episode as the only symptom. REFUTED FINDINGS, which I checked and which the implementer was told NOT to act on: the review claimed the heavy-detector roster might be dead code — the eight names are all present in the 78-entry `_DETECTORS` roster AND the gate reaches them on its own path (`dispatch.py:5440` calls the gate for every detector, and the roster check at :650 is what the gate tests), so the roster is neither unregistered nor unreached; and the review claimed `state.atomic_write` might not exist — it does, at scripts/lib/state.py:253, with exactly the signature used. THE SCOPE SPLIT, and it is the actionable outcome: the pressure gate lands on its own, once the rework is reviewed; A-2 does NOT ship with it and stays an OPEN FINDING on TRDD-ZIKYQQY0, to be reworked with the environment captured BEFORE the kill. A change that cannot be observed to work, that weakens a kill's audit guarantee from guaranteed to best-effort, and that hands a foreign process a write primitive, is not fit to ship alongside a pressure gate — and the pre-A-2 shape is the SAFER of the two ledger destinations, though still not a lossless one.
