# The janitor collects the anomalies it sees and opens a card for each one by itself

Owner directive, 2026-10-05, verbatim: "do you realize that this exact procedure, of collecting the anomalies and open a TRDD for each one with investigate-verify-fix goal, is the thing that the janitor should do by itself?"

Context: on 2026-10-05 a session found more than fifty anomalies by hand (false rotator verdicts, a process larger than the machine's memory, a task that overran its budget many times over, an unexplained tick failure, leftover files, a worker looping on a failing command) and opened one card for each only when the owner asked, twice. Most of them were already visible in the janitor's own logs and state as single lines nobody collected.

What exists today, as seen in that session and NOT yet read in the code: detectors write advisory findings to a ledger and print some as drift lines; some classes of finding become support tickets that a repair agent works; nothing was seen that turns a finding into a card on the board, and lines such as 'exited 1', 'evaluation failed', 'budget exceeded', 'timed out' in the daemon's log were not seen to become findings at all.

Wanted: the janitor itself (1) harvests anomalies from its own logs, state and detectors, including the ones that are only a log line today; (2) deduplicates them against open cards and against each other; (3) opens one card per anomaly with the goal to investigate, verify and fix the root cause, stating what was observed and what is not yet verified, with no private data in a project card; (4) reports only the count to the conversation.

To settle in design before any code: which scope a card gets when the anomaly is about one machine; a cap so a noisy detector cannot flood the board (the hand-made batch of that day already holds duplicates and overstated wording, as its reviews showed); who may open a card unattended; how this relates to the existing findings ledger and ticket path, which must be read first. The fifty-odd cards opened by hand that day are the worked example and the first test set.

## What exists (read in the code by two workers, 2026-10-05)

A detector calls issue_catalog.raise_issue(code, where, evidence). For a harness kind it opens a ticket; for a project kind ticket_proposal.propose writes a proposal card. Both carry the same dedupe key (code plus where), and a repeat with the same key joins the existing ticket or returns the existing open proposal. clear_issue and reconcile withdraw a proposal when the finding clears. 14 of 75 detectors use this path; 60 never reference it and print free-text lines. The rotator alert line and the background-worker line are printed directly by the dispatcher on every fire, outside both the seen-once mechanism and the card path. Advisory lines are recorded in the findings ledger under one code per detector, once per repeat. Nothing reads the daemon log or the per-detector failure stamps for error-shaped lines. The limits of 2 per heartbeat and 20 per day cap how many tickets are DISPATCHED to a repair agent; opening a ticket or a card is not limited, and an over-limit ticket is deferred, not dropped. Where an anomaly can be lost today: a detector raises at most 5 per fire, so a transient sixth is lost; an unknown code returns not-ok and is only logged; the refusal gate; and every detector that never calls raise_issue. propose compares only with open proposals: a card promoted to tasks, closed, archived or made by hand is not matched. Proposal cards are written directly as files, not through the card tool, with no author field, and nothing commits them. The Jev client may not be imported by the dispatcher, the daemon, any detector or any hook; a separate script run as its own process is the permitted form. No project rule covers sending text to an outside model, and the Jev path has no secret filter.

## Design (draft 2, 2026-10-05, waiting on the owner's decisions below)

Order of work, each its own card. STEP 1, first because it relieves the owner at once and needs no cards, no Jev and no identity work: the lines the dispatcher prints directly (rotator alert, background-worker count) and the memory lint count go through the existing seen-once mechanism, so an unchanged line is printed once. An anomaly on the never-silence list is exempt. STEP 2, one key per anomaly: every printed anomaly gets a catalog code and a where; advisory detectors get a where per finding instead of one code per detector; a generic 'unclassified' code keyed on the normalised line catches what matches nothing, so a novel anomaly is carded and not lost. STEP 3, every detected anomaly reaches a card: the 60 detectors and the direct prints call raise_issue; a new slow detector harvests the per-detector failure stamps and error-shaped daemon log lines; the per-fire cap defers and never drops (the overflow is persisted and raised on the next fire). Making a card is never limited; only dispatching a repair agent is. STEP 4, covered means silent, with exceptions: before printing, the key is looked up among proposals, tasks, closed and archived cards and live tickets, from an index kept by the slow pass and not rebuilt on every fire. Covered: not printed. Not silenced: the never-silence list; a covered anomaly whose severity rose or whose evidence changed; a covered anomaly whose card is closed (a new card is opened and linked to the old one). The first sight is printed once with the card id. The same rule governs the desktop alert and the findings lines at session start. STEP 5, merging by meaning: a separate script, run by the daemon as its own process on a slow interval, asks Jev whether a new anomaly matches an existing card. A match is written on both cards as a PROPOSED merge with the reason. The janitor only appends; a session applies the merge by rewriting the card into one account. Jev unavailable: the anomaly keeps its own card marked 'possible duplicate'. Machine-private anomalies go to local cards and are never sent out. PREREQUISITE for steps 3 to 5: cards are created through the card tool with a stated author, and the unattended identity is settled. FIRST WORKED CASE: the 59 cards opened by hand on 2026-10-05 are merged by hand with step 5's rules, to fix those rules before code. NOT COVERED: an anomaly that only a session finds by reading code or reviewing; that still needs a session.

## What the owner's specification settles and what it leaves open (session's reading, 2026-10-05)

SETTLED by the owner's six steps: Jev is the means of the existence check (asked decision 5 is answered yes; how much text is sent is still open). The janitor appends or integrates into an existing card itself (asked decision 2 is answered: it may write into an existing card). There are two destinations for a new anomaly: a card of a new type IVF (investigate, verify, fix) or, for a minor maintenance issue, a janitor ticket; the owner's examples of minor are file clean-up, wrong folders, outdated dependencies, missing linters, broken memory, wrong scope. The user is warned ONCE, on the first detection only. Agents are reminded of pending cards when idle: the reminder goes to agents, not to the user as a repeated warning. DIFFERS from draft 2: the check for an existing card happens on every new anomaly and uses Jev, not only in a slow later pass; draft 2's exact-key lookup remains useful as the cheap first test before Jev is asked. NEW WORK the specification adds: a task type IVF does not exist in the card tool's list of types and must be added there (the card tool belongs to another project); a classifier that decides between an IVF card and a ticket; the idle reminder (a card reminder detector exists and must be read first). STILL OPEN, the owner's to decide: which anomalies are warned about more than once because they are emergencies or have worsened (the specification says once; the session proposes an exception for an expired login, a leaked credential and a runaway process); whether cards may be written into other projects' trees; whether an unattended card is committed automatically; what is done when Jev is unavailable (the session proposes: open a separate card marked possible duplicate, never drop); the order against the memory guard card.
