# TRDD-bc16d602 — Memory wiki: the three core skills

## ⏵ STATE — READ THIS FIRST ON RESUME (authoritative) — 2026-06-10

**Goal (user vision, 2026-06-10):** upgrade Claude Code memory from a FLAT PILE
of atomic `.md` notes into a true navigable WIKI. When an agent is about to work
on a FILE that belongs to a functionality (frontend, backend, db, a render
engine, a parser, a controller, an endpoint, a scraper, a deployer, a logger…),
memory surfaces that functionality's **hub page** — the tip of the iceberg: the
overall view + the big general decisions + links DOWN to the detail. From the tip
the agent navigates progressively (read only the links the task needs — exactly
like Skill reference autodiscovery).

**The pyramid is NOT a strict tree.** It uses:
- **EXPAND** → an `aspect` page when a memory is a GENERAL rule shared by many
  components/procedures (style-system, fonts, dialog-forms, error-envelope).
- **REDUCE** → a `component` page when a memory is specific to ONE element
  (login-panel, user-model, checkout-endpoint).
- **one-component-one-page invariant:** all of an element's memories live in ONE
  page; the style aspect and the interaction aspect link to the SAME component
  page, never two — the graph CONVERGES on shared component pages.

**Every page carries CONTEXT, not just memories:** a mandatory `## See also`
section linking to everything that relates to/influences the subject (general
styles, view/model design, api functions, graphic items, animations, db,
downstream consumers). That context web is what makes the wiki explorable.

**LOAD-BEARING UPDATE RULE (user, emphasized 2026-06-10):** whenever an UPDATE
SUPERSEDES an existing memory — a corrected fact, a reversed decision, a changed
value, an abandoned approach — the OLD memory is **NEVER deleted**. The body is
cleaned to the current truth, and the superseded statement is **demoted to a
dated lesson-learned / note** (`[^N]` footnote under `## Notes and lessons
learned`) carrying the WHY (the root cause / why it changed). This is a top-level
invariant of EVERY update, not only explicit "corrections" (RULE 0 + the
Bug-Autopsy directive: every fixed mistake becomes a guardrail).

**Architecture split (user):** the THREE SKILLS are the CORE (the rules for
MEMORIZING, UPDATING, RECALLING). **memgrep is only the instrument.** The
**janitor background layer** (aggregate, dedup, add missing references, correct
errors, keep the wiki consistent) is an ADDITIONAL layer that prevents drift —
not the core.

### Load-bearing facts / gotchas

- memgrep already supplies the graph primitives: `links --to/--from/--broken/
  --orphans`, `--where 'links-to/linked-from "<page>"'` semijoins, `fm.KEY`
  frontmatter queries (so `fm.tier`/`fm.functionality`/`fm.globs` are queryable).
  No memgrep change is required for the skills to work; a dedicated "which hub's
  glob matches FILE" helper would be a nice-to-have (today the skill lists hubs
  and matches globs itself).
- Backward-compatible: existing `node_type: memory` notes with no `tier` are
  treated as `component`; the wiki emerges incrementally (no migration event).
- Skill `description`s kept under ~200 tokens; SKILL.md bodies 134-173 lines;
  model 189 lines.
