# TRDD-bc16d602 — Memory wiki: the three core skills

## ⏵ STATE — READ THIS FIRST ON RESUME (authoritative) — 2026-06-10

**Goal (user vision, 2026-06-10):** upgrade Claude Code memory from a FLAT PILE
of atomic `.md` notes into a true navigable WIKI. When an agent is about to work
on a FILE that belongs to a functionality (frontend, backend, db, a render
engine, a parser, a controller, an endpoint, a scraper, a deployer, a logger…),
memory surfaces that functionality's **hub page** — the tip of the iceberg: the
overall view + the big general decisions + links DOWN to the detail. From the tip
the agent navigates progressively (read only the links the task needs — exactly
like Skill reference autodiscovery).

**The pyramid is NOT a strict tree.** It uses:
- **EXPAND** → an `aspect` page when a memory is a GENERAL rule shared by many
  components/procedures (style-system, fonts, dialog-forms, error-envelope).
- **REDUCE** → a `component` page when a memory is specific to ONE element
  (login-panel, user-model, checkout-endpoint).
- **one-component-one-page invariant:** all of an element's memories live in ONE
  page; the style aspect and the interaction aspect link to the SAME component
  page, never two — the graph CONVERGES on shared component pages.

**DIRECTIONAL edges (user refinement, 2026-06-10 — the centerpiece):** the wiki is
COLLABORATIVE (Wikipedia-style — any agent edits). Links are TYPED by the
EXPAND/REDUCE topology, NOT a flat "see also":
- An EXPAND page (general/aspect/hub) **RADIATES** — it is a sun carrying a
  `## Applies to` ray-list DOWN to EVERY element it governs (`frontend-style`
  links ALL components). Creating it grows the system's *configurations*.
- A REDUCE page (component) **RECEIVES** — a terminal carrying a `## Governed by`
  list UP to every general page that rules it; it lists NOTHING downstream (it
  governs nothing). `## See also` is reserved for genuinely lateral relations.
- `Applies to` ↔ `Governed by` are the two halves of one edge (kept reciprocal;
  the librarian backfills one-sided edges).

**WHY (the success criterion):** shared rules are written ONCE in radiating
pages; components stay LEAN (a fixed body + pointers up), never re-copying a rule.
A 100-memory page collapses to ~12 + links; the pyramid SLIMS toward the base
(the base can be less populated than the abstract layers). Result: compact,
non-redundant, and **cacheable** — an agent reads a shared sun ONCE and reuses it
across every component pointing at it, so navigation costs the strict minimum
tokens. EXPAND grows the "wardrobe" of configs; REDUCE adds a fixed "wearer".

**LOAD-BEARING UPDATE RULE (user, emphasized 2026-06-10):** whenever an UPDATE
SUPERSEDES an existing memory — a corrected fact, a reversed decision, a changed
value, an abandoned approach — the OLD memory is **NEVER deleted**. The body is
cleaned to the current truth, and the superseded statement is **demoted to a
dated lesson-learned / note** (`[^N]` footnote under `## Notes and lessons
learned`) carrying the WHY (the root cause / why it changed). This is a top-level
invariant of EVERY update, not only explicit "corrections" (RULE 0 + the
Bug-Autopsy directive: every fixed mistake becomes a guardrail).

**Architecture split (user):** the THREE SKILLS are the CORE (the rules for
MEMORIZING, UPDATING, RECALLING). **memgrep is only the instrument.** The
**janitor background layer** (aggregate, dedup, add missing references, correct
errors, keep the wiki consistent) is an ADDITIONAL layer that prevents drift —
not the core.

### Session 3 — SIMULATIONS (user: "find all potential issues and shortcomings")

10 empirical sims against the real memgrep + librarian (full report:
`reports/memory-system/20260610_204509+0200-wikimem-simulation-findings.md`).
Outcomes:
- **2 librarian bugs FIXED** (+2 regression tests, suites 57/57): fence-blind
  body scan false-positived a component whose body shows `## Applies to` inside
  a code EXAMPLE (S10b); flow-style `metadata: {tier: …}` was invisible to the
  tier checks (S10a).
- **Scope-local link law ADDED** (S2): the link graph is per-root, so
  cross-scope wikilinks are forever-broken to the librarian AND broken for
  other devs when a PROJECT page back-links a LOCAL page → wikilinks may only
  target the SAME scope root; cross-scope references in prose. Encoded in the
  model's new "Link hygiene" + MEMORIZE wiring.
- **RENAME move ADDED to UPDATE** (S6): one rename = N instant broken inbound
  links; protocol = repoint inbound (`links --from`) FIRST, then rename
  file+frontmatter+index, then re-audit.
- **Link hygiene documented** (S4/S7/S8/S9): page-level links (anchors resolve
  but reciprocal is page-level); no spaces in targets; case-insensitive
  resolution; globs are repo-relative; unique names across scopes; lessons'
  links are real edges.
- **Confirmed strong** (S1/S3/S5): multi-root recall works as documented (tie
  order = arg order = the documented precedence); memgrep links are
  fence-aware; 66 pages/730 edges → ~2 ms law audit, zero false findings,
  precise recall.

### Load-bearing facts / gotchas

- memgrep already supplies the graph primitives: `links --to/--from/--broken/
  --orphans`, `--where 'links-to/linked-from "<page>"'` semijoins, `fm.KEY`
  frontmatter queries (so `fm.tier`/`fm.functionality`/`fm.globs` are queryable).
  No memgrep change is required for the skills to work; a dedicated "which hub's
  glob matches FILE" helper would be a nice-to-have (today the skill lists hubs
  and matches globs itself).
- Backward-compatible: existing `node_type: memory` notes with no `tier` are
  treated as `component`; the wiki emerges incrementally (no migration event).
- Skill `description`s kept under ~200 tokens; SKILL.md bodies 134-173 lines;
  model 189 lines.
