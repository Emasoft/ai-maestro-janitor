# TRDD-3ab0397e — Heartbeat survival on CC 2.1.173 (issue #23)

## ⏵ STATE — READ THIS FIRST ON RESUME (authoritative) — 2026-06-11

**Source:** janitor#23 (filed 2026-06-11 by a user-side Claude session, evidence-grade).
Two ACCEPTED findings; maintainer triage + chosen directions posted on the issue.

### Finding 1 — `CronCreate(durable: true)` silently downgraded to session-only (CC 2.1.173)

Evidence: runtime replied "Session-only (not written to disk)"; `~/.claude/scheduled_tasks.json`
ABSENT; project-local `.claude/scheduled_tasks.json` exists but `tasks: []`. The overnight
rate-limit-survival architecture (TRDD-1222f06a §9) assumes durable persistence across restarts.
Mitigating reality: the SessionStart hook nudges `/janitor-arm` every session start, so an
interactive restart re-arms on its first turn; the genuinely-lost case is the headless window
(crash → no session → no nudge) — exactly what durable existed for.

**Plan (1a — detect, don't trust):** after `CronCreate`, the `janitor-arm` skill instructs a
read-back of BOTH scheduled-task stores (`~/.claude/scheduled_tasks.json` + project-local);
if the new job id is in neither, the arm output MUST say
"armed SESSION-ONLY — durable downgraded by this Claude Code build; the SessionStart nudge
re-arms each session" instead of claiming durable success.
**Plan (1b — document):** janitor-architecture.md gains the limitation note.
**Plan (1c — upstream):** verify on ≥2.1.173 and file on the Claude Code repo if confirmed
(a silently-ignored `durable: true` is an upstream contract break regardless of our mitigation).

### Finding 2 — `${CLAUDE_PLUGIN_DATA}` not stable across load-source changes

Same plugin resolved to `…/ai-maestro-janitor-inline/` (inline load) and
`…/ai-maestro-janitor-ai-maestro-plugins/` (marketplace load) within ONE session → the armed
cron kept firing the OLD stub path; orphan dirs accumulate. Independently corroborated on this
machine (both dirs present, stubs byte-identical).

**DECISION — option 2+3 from the issue, NOT option 1:** no fixed unofficial
`~/.claude/plugins/data/<name>/` path (that abandons the documented per-plugin DATA-dir
contract — backup/purge semantics — that the janitor itself preaches in CLAUDE.md). Instead:

- **2a (drift detect + auto-rearm):** the per-session path (dispatch heartbeat or the
  SessionStart hook) compares the LIVE `${CLAUDE_PLUGIN_DATA}/dispatcher-stub.py` path against
  the path the armed cron targets (recorded at arm time in a state file, e.g.
  `<state>/heartbeat-stub-path.txt`); on mismatch → emit the existing `[janitor-renew]` marker
  so Claude silently re-arms (re-using the renew machinery — no new surface).
- **2b (orphan migration):** `/janitor-arm` (the skill's stub-install step) detects sibling
  `ai-maestro-janitor-*` data dirs whose stub is byte-identical and retires the stale one
  (safe-delete / leave a tombstone README) so orphans don't accumulate.

### NEXT ACTION
Implement 1a (read-back + honest arm output) + 2a (drift detect → `[janitor-renew]`) first —
both are small and self-contained; then 2b orphan migration; then 1b doc + 1c upstream check.
Rides the next publish (v0.7.0 just shipped; this targets v0.7.x).

## Why this exists
The heartbeat is the janitor's wake-up spine: every recovery loop (rate-limit resume,
compact resume, daemon lazy-spawn) assumes it fires. Both findings are silent contract breaks
that only show up exactly when the system is needed most (restarts, load-source changes).
