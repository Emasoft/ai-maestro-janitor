# An unreleased fix is not a fix, and the gap must be escalated

THE INCIDENT THIS CARD WOULD HAVE PREVENTED, and it is the reason the card exists. On 2026-10-20 the owner complained that janitor alerts repeat on every heartbeat fire. The fix was ALREADY WRITTEN and COMMITTED on 2026-10-19 (f795816c, TRDD-JWIGGMH0) and the machine still repeated the alert, because the fix was 599 commits behind the v3.8.11 release. For four days, and across at least three separate diagnosis cycles, the alert was the only signal anyone had — and the one detector that could have named the real cause, repo-state, reported it as a LOW ADVISORY that the quiet filter DROPS. So the janitor was, in effect, telling the owner "your repo is dirty" while the actual fact was "your installed artifact is 599 commits behind your own working tree, and the fix for the thing you are complaining about is in that gap". Every agent cycle re-diagnosed the symptom correctly and re-committed the fix, and the fix never reached the machine. A card about the RELEASE (TRDD-PWL9GD4E) fixes this instance; this card is the one that would have made the instance VISIBLE in time.

THE GAP, MEASURED. 599 commits sat on main after the v3.8.11 release; the installed plugin was the newest CACHED version, and the fix was not an ancestor of that release. The two numbers a detector could have compared — commits on main since the last release tag, and the version of the code the heartbeat actually runs — were both available, and nothing compared them.

THE MECHANISM, and it must be a detector not a rule, because the whole point is to be SEEN. The janitor already has the primitive: repo-state.py computes exactly the right number (commits on the branch since the last release tag that were not made through publish.py) and prints it — and the quiet filter records that line into the findings ledger at sev="LOW" (dispatch.py:857-858), where it does not reach a model turn. The change is not a new detector; it is a SEVERITY THAT SCALES WITH THE GAP, and a rule that an unreleased gap of a certain size is not an advisory but a condition. The threshold is the design question: a repo that is one commit ahead is dirty and should stay quiet; a repo whose SHIPPED ARTIFACT is hundreds of commits behind its own working tree is running code that does not contain the fixes its own tree holds, and every alert caused by that code is unfixable until a release happens. Somewhere between those is the line, and the line belongs to the owner, not to a default.

WHY IT IS NOT THE SAME CARD AS THE RELEASE, and why it is not the same card as the prevention mechanism. TRDD-PWL9GD4E is about cutting one release. TRDD-5CGPEK4V is about a condition that repeats on every fire and no agent can act on. This card is the case that is BOTH: a condition that repeats on every fire, that no agent can act on (the agent cannot publish), and that is invisible because the detector that knows about it is an advisory. It is also the case where the "agent can act on it" answer is WRONG in an instructive way — the agent CAN act on it, by cutting a release, but only with the owner's authorisation, so it is exactly the boundary case the classification in TRDD-F3LVCQ39 must get right. That is why the census's actionability axis has to be able to say "actionable, but only by the owner, and only after an authorisation that is not a per-fire decision".

THE COST OF GETTING IT WRONG, in both directions, because the failure is not one-sided. TOO QUIET (today's behaviour) and a machine runs stale code for days while its owner is told nothing, and every symptom of that staleness is misdiagnosed as a live defect. TOO LOUD and a repo that is legitimately mid-development — 599 commits is a plausible state for a working tree — raises a HIGH finding on every fire, which is the same noise problem TRDD-5CGPEK4V exists to fix, and it would teach the owner to dismiss it. The threshold therefore has to distinguish a repo that is ABOUT TO RELEASE from a repo that has ABANDONED the release, and the only signal that distinguishes them is the same one: age. A gap that has not moved for N days is not a repo about to release; it is a repo whose fixes are unreachable. So the escalation is age-based, not count-based, and the count is a secondary input.

ACCEPTANCE. (1) A detector (or the existing repo-state, re-classified) raises a condition when the gap between the branch and the last release tag is non-trivial in AGE measured against the repo's own historical maximum release interval, and is above a stated size floor, and the severity of that condition is above LOW, so it REACHES a model turn rather than being dropped by the quiet filter. The size floor is a floor, not a conjunct: a repo that ships a handful of commits and then stops for longer than its own historical maximum has its fixes just as unreachable as one with a large gap, so AGE is the operative signal and the size only keeps a lightly-dirty tree quiet. (2) The line names the concrete fact — how many commits, since which tag, how old — and names the consequence, that the running plugin is an OLDER build than the tree and cannot contain the tree's fixes. (3) A repository that is a few commits ahead and releasing this week does NOT raise it, and a test asserts that. (4) A repository whose gap has not moved for the threshold period DOES raise it, and a test asserts that. (5) The condition is classified in the actionability vocabulary of TRDD-F3LVCQ39 as one the agent may not resolve alone, so TRDD-5CGPEK4V's mechanism handles it correctly rather than treating it as a repeating actionable line. (6) The threshold is the owner's to set, and the default is documented rather than silently chosen.

THE THRESHOLD, MEASURED ON THIS REPO'S OWN RELEASE HISTORY, and the measurement CHANGED THE DESIGN. A commit COUNT turns out to be the wrong signal for this repo: the inter-release commit counts are tiny and ordinary — v3.8.1 through v3.8.11 shipped 7, 34, 28, 30, 22, 19, 41, 17, 3, 29 and 18 commits apart — so a threshold of even 50 commits would never have fired, and 599 (the size of the gap as measured on 2026-10-20 01:31) is not a number this repo's own history produces. The RELEASE CADENCE is the signal. Measured over the 38 releases in the retained tag history (2026-07-16 to 2026-10-07, 37 intervals): the days between consecutive release dates have median 1, mean 2.24, p90 6, and MAX 8; only 6 of 37 intervals were 4 days or longer. THE CURRENT GAP IS 13 DAYS — longer than every one of those 37 intervals. So the honest threshold is stated in the repo's OWN units and is self-calibrating: a release gap that exceeds the repo's historical MAXIMUM release interval is not a repo about to release, it is a repo whose fixes are unreachable — and that is exactly the state this incident was in, and it was detectable from the tag history alone, with no new instrumentation. The threshold's BACKTEST is stated here too, because a threshold that has never been run against the history it is derived from is a guess: measured over those same 37 intervals, a rule that fires on a gap exceeding the repo's own historical maximum fires ZERO times — the maximum equals the maximum by construction, so it can only fire on a gap the repo has never had — and the one gap it DOES fire on is the present 13-day one, which is the first in this repo's history to exceed the maximum. A p90 threshold, by contrast, fires 3 times in those 37 intervals (or 4 if the threshold is stated as 6 inclusive), on the 7-day and the two 8-day gaps. That low sensitivity is a real property of a maximum-based rule, not an accident: the maximum IS the worst gap the repo has ever had, so a rule keyed to it fires only on a record-breaking gap, and once it fires the maximum has moved. The honest form of the threshold therefore carries an absolute floor, and the card leaves that floor to the owner alongside the measured distribution (median 1, p90 6, max 8, current 13). The 13-day figure is also why the alert was unfixable in the loop: each diagnosis cycle added commits, so the gap's SIZE grew while its AGE kept climbing, and neither moved the machine.

NEXT ACTION: the RULE IS BUILT AND GREEN — 800bc036 (the escalation), 7a42c622 (C1/C2/C3/N2) and 82d16c3d (three review findings: the non-release-tag subtraction, the block that was nested under the checked-out branch, and the docstring that did not match the code). The remaining work is the OWNER'S threshold: the bar is the repo's own historical MAXIMUM release interval, and the card's measured distribution (median 1, p90 6, max 8, current 13) must be put to the owner to set the absolute floor that a maximum-based rule needs. The rule also has two owner-set knobs already in place: CLAUDE_PLUGIN_OPTION_RELEASE_GAP_MAX_DAYS (the bar) and CLAUDE_PLUGIN_OPTION_RELEASE_GAP_MIN_COMMITS (the size floor, default 5). Acceptance clauses (3), (4) and (5) still need the owner's ruling on the floor.
