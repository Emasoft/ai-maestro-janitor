# The janitor must detect host resource exhaustion, and kill only what Claude Code caused

THE INCIDENT, MEASURED, NOT HYPOTHETICAL. On 2026-10-20 at 10:41:37 this macOS 64 GB box panicked the kernel: `watchdog timeout: no checkins from watchdogd in 90 seconds`, with `Compressor Info: 100% of segments limit (BAD), 69 swapfiles`. The reboot followed 27 seconds later (kern.boottime 1792485724 = 10:42:04). The file's own mtime of 11:33 is when CrashReporter WROTE it, not when the crash happened — the panic log's `Calendar:` epoch field (0x6ad72941) resolves to 10:41:37. The macOS jetsam snapshot from the same memory episode (JetsamEvent-2026-10-20-120837.ips) recorded 986 processes holding 19.8 GB RSS: 8 concurrent `claude` CLI sessions at ~6 GB, 21 `node` at 1.8 GB, 12 Codex renderers at 1.8 GB, 33 `agentlenspro` statusline processes at 329 MB, WindowServer+iTerm2 at 2.3 GB.

THE GAP THAT LET IT HAPPEN, and it is precise. The janitor measures free memory and NOTHING ELSE about host pressure. `scripts/lib/memory_guard.py` reads free memory via `parse_vm_stat` and compares it to `DEFAULT_MIN_FREE_MB` (1024); `scripts/detectors/host-load.py` measures load average only (bar = cores x 4 = 56 on this host). NO code anywhere in the janitor reads `vm.swapusage` or `Pages occupied by compressor` — grep for `swapusage` and `compressor` across scripts/ returns nothing but two unrelated false positives (a font-parsing regex and a protobuf field). The panic's own diagnosis was a COMPRESSOR-AT-SEGMENT-LIMIT condition with 69 swapfiles: the box had 64 GB of RAM and died under SWAP exhaustion, which is precisely the class of exhaustion the free-memory probe cannot see. Measured on the host after the reboot, `free_memory_mb()` returned 736 MB — below the 1024 floor, so the existing guard WAS firing — and it could see neither the swap nor the compressor, and (below) could not act on what it did see.

THE SECOND GAP: WHAT THE GUARD IS ALLOWED TO KILL. `memory_guard.py` confines kills to `JANITOR_WORKLOAD_SIGNATURES` — six narrow janitor-spawned shapes (`claude plugin update`, `claude plugin marketplace update`, `claude plugin list`, `oauth_rotator/*.py`). `_CLAUDE_ANYTHING` plus a signature-index check makes every OTHER `claude`-shaped command — the user's interactive session — categorically non-killable, and the code calls that "the Tier-1 safety contract's load-bearing clause". `scripts/daemon.py::task_memory_guard` says so in its own docstring: "Tier 2 (kill the biggest non-interactive process at critical pressure) is NOT implemented — per Decision 1 it stays off the table without a fresh user sign-off; there is deliberately no code path or enabling flag for it." So the machinery to kill a runaway EXISTS and is well-built (one victim per beat, SIGTERM then SIGKILL with a grace period, protected-pid set, loud logging, a process snapshot to a file for forensics); what does not exist is the authority to kill a runaway that Claude Code caused but the janitor did not spawn — which is the whole of the 2026-10-20 incident.

THE OWNER'S DIRECTIVE (2026-10-20), which is this card's mandate: "add a janitor daemon monitoring the system and detect all those runaways and resource exhaustions dangers, and prevent the system crash by killing the processes causing this. But every time a process is killed by the janitor daemon, a message must be broadcasted to all agents reporting exactly what process was killed and why, so the agents will not repeat the same mistake again. But you must only kill processes started by the agents or started by plugins that installed daemons autoexecuted at boot. Do not touch processes executed by other ai clients like codex or copilot, etc. The janitor will only be responsible for the processes caused by claude code directly or indirectly (also claude desktop, if it is possible to handle those sessions too, but not the claude cloud sessions or claude.ai sessions)."

WHY THIS IS A SEPARATE CARD FROM TRDD-DKID2PYP, and not a clause in it. DKID2PYP governs the guard's intervention on a runaway PROCESS THE JANITOR OWNS, and carries the owner's 2026-10-05 policy verbatim: "intervention on other processes is kept to a minimum; on a runaway or another emergency the janitor may intervene, in this order: log it, make sure the work can be resumed or restarted with no loss of data, context or goals, only then stop the process or tool, fix, resume the work." Its measured findings (2026-10-05) cover kill and freeze semantics on test-started processes: a frozen file-lock holder blocks every other taker; a killed fastedit batch-edit/multi-edit left files whole and the pair consistent in every interrupted run; a kill signal always takes effect. That foundation is real and is reused here. What DKID2PYP does NOT cover is a runaway caused by the USER'S OWN SESSION TREE — a different victim class, a different trigger, a different default, and therefore a different authority. Decision 1 (2026-05-31) reserved Tier 2 for exactly this and demands a FRESH sign-off; this card is that sign-off, and per the advisor's verdict it needs its OWN opt-in switch rather than a clause inside a default-on chore.

THE ADVISOR'S VERDICT (2026-10-20), which reshapes the design in five specific ways. (1) THE INTERACTIVE `claude` SESSION MUST BE CATEGORICALLY NON-KILLABLE. My first draft made "it is a `claude` process" sufficient for attribution; among killable candidates on this box the user's own session IS the largest (~1 GB each), and the session is a DESCENDANT of the user's shell, never an ancestor, so the "never kill a live session's ancestor" carve-out does not save it. Killing the session the user is typing into is the single most likely harm of the naive design. (2) ANCESTRY IS A NECESSARY BUT NOT SUFFICIENT FILTER, and the "started by a launchd agent a Claude Code plugin installed" clause is SELF-KILLING: the janitor installs exactly one launchd agent (`com.ai-maestro-janitor.daemon`), so that clause makes THE JANITOR DAEMON itself a kill candidate — and it sweeps in `com.cblh.codex-app-server.plist`, which is exactly the Codex daemon the owner forbade touching. A process whose command line references `~/.claude/`, `/share/claude/versions/` or `plugins/cache/`, or whose environment carries `CLAUDE_PROJECT_DIR` / `CLAUDECODE` / `CLAUDE_PLUGIN_DATA`, is Claude-attributable REGARDLESS of reparenting — which is the channel the statusline churn needs, since a reparented-to-launchd process has no `claude` ancestor at all. (3) ATTRIBUTION PROVES RELATEDNESS, NEVER KILL-WORTHINESS: a positive allowlist of runaway SHAPES among the attributed candidates is required, exactly as `JANITOR_WORKLOAD_SIGNATURES` embodies for janitor-owned workloads, plus the age gate `DEFAULT_RUNAWAY_ETIME_S` already implements. Without it the rule degenerates to "biggest process wins", which is what Decision 1 refused. (4) THE BROADCAST MECHANISM IS THE `rotator-alert.json` PATTERN, not a write into every project's state dir: the daemon writes ONE file into the global-state dir, and `dispatch.py::_phase_rotator_alert` (scripts/dispatch.py:2186) prints ONE drift line per session before the summary-hold gate. The population of sessions is `fleet_scan.gather_fleet()`'s live `project_root`s, not "every project" — the daemon does not know the project set. The drift line must be DESCRIPTIVE, never imperative ("killed pid 1234 node … swap exhausted"), because this codebase has already been burned by imperative status lines being executed by autonomous readers. (5) IT MUST BE A NEW CHORE, DEFAULT-OFF, REGISTERED IN `harness_backend.GLOBAL_CHORES` — `tests/test_harness_backend.py` asserts that dict matches daemon.py's Task registry name-for-name and default-for-default, so a new chore without the entry fails the suite. It cannot ship as a clause inside `memory-guard`, which is default-ON and whose Tier-1 truth table is unit-tested under a user-signed contract: two kill authorities on one host with disjoint protected-pid sets can race, and a brand-new authority cannot be default-off inside a default-on chore.

WHAT EXISTS AND MUST BE REUSED, NOT RE-IMPLEMENTED. `scripts/lib/state.py` already has `parse_ps_table` (line 987), `process_ancestry` (line 1006), `is_claude_command` (line 1033) and `claude_ancestor_pid` (line 1046) — the ancestry machinery, with the hook case already documented ("a hook is launched through bash -> uv -> python; only a walk finds it"). `scripts/lib/memory_guard.py` has `ProcRow` (pid, ppid, rss_kb, etime_s, command), `snapshot_processes`, `select_victim`, `select_refused_alert`, `kill_process(pid, term_grace_s=2.0)`, `free_memory_mb`. `scripts/lib/rotator_alert.py` has `drift_parts(root, now)` for the daemon->session channel. `scripts/lib/fleet_scan.py` has `Instance` (pid, command, tty, project_root, terminal) and `parse_ps_claude`.

THE MEASUREMENT THAT SHAPES THE HOST-PRESSURE PROBE. The panic's diagnosis was `100% of segments limit (BAD), 69 swapfiles`. The signals that carry it are `vm.swapusage` (total/used/free plus the swapfile count) and `Pages occupied by compressor` from `vm_stat`, both readable on this host: `sysctl -n vm.swapusage` and `vm_stat | grep 'Pages occupied by compressor'`. The free-memory probe alone cannot see the condition that actually killed the machine, so the probe must gain swap and compressor terms — and the threshold must be stated in terms of the SIGNS OF EXHAUSTION, not of free memory alone.

THE BROADCAST MUST SATISFY THE PER-PROJECT CHANNELING INVARIANT (TRDD-X92VBFNF, owner directive 2026-07-17, VERBATIM): "an AUTOMATIC surface (heartbeat drift line, detector output, injected nudge, proposal TRDD, notification) may carry information about EXACTLY the project it fires in — never another project's findings, names, or even aggregate counts that include them. Four independent reasons: wrong skills; agents are FORBIDDEN from acting on other agents' workdirs/gits/repos; token-budget contamination breaks the division of responsibilities; data exfiltration into projects with weaker (possibly zero) data protections. Only EXPLICIT HUMAN COMMANDS may be machine-wide." A kill event is about the HOST, not about a project, so it is legal ONLY as a HOST-LEVEL payload that is IDENTICAL for every project — which is exactly what the generation+ack pattern already does for the gh-notify-inbox, and what `rotator-alert.json` does for the rotator. THE CONSEQUENCE FOR THE PAYLOAD: the kill record may name the pid, the process's BASE NAME, its RSS, its age and the pressure readings — but NOT a project path, NOT a project name, and NOT a command line that carries one, because a command line like `pytest /Volumes/.../other-project/tests` would carry one project's content into every other project's session. The command line is therefore REDACTED to its base name in the broadcast copy, and the FULL command line goes only to the daemon's own log and to the affected project's own ledger entry. This is a design constraint on the broadcast shape, not an afterthought: it is the difference between a legal host-level signal and a channeling violation.

ACCEPTANCE. (1) A NEW DAEMON CHORE, default-off, registered in `harness_backend.GLOBAL_CHORES` and daemon.py's Task registry, that on each beat reads the host-pressure signals (free memory, swap usage and swapfile count, compressor occupancy) and reports a PRESSURE STATE — healthy, elevated, critical — with the readings that produced it. (2) The pressure probe reads SWAP and COMPRESSOR, not free memory alone, and a test asserts that a host simulated as swap-exhausted with healthy free memory still reports CRITICAL. (3) When the host is CRITICAL, the guard selects AT MOST ONE victim per beat by the discipline `select_victim` already embodies: the largest-RSS process that is BOTH (a) attributable to Claude Code, by ancestry OR by a `~/.claude/` / `plugins/cache/` / `CLAUDE_*` environment signal, AND (b) matching a POSITIVE allowlist of runaway shapes, AND (c) older than the age gate, AND (d) not a protected pid, AND (e) NOT an interactive `claude` session. (4) A test asserts that an interactive `claude` session is NEVER selected as a victim even when it is the largest process on the host — this is the load-bearing safety test. (5) A test asserts that a Codex, Copilot or LM Studio process is never selected, including one whose ancestor chain reaches a `claude` session, and that the janitor's own daemon and its launchd agent are never selected. (6) The kill uses the existing `kill_process` discipline — SIGTERM, grace period, SIGKILL — and the guard never kills more than one process per beat. (7) EVERY KILL IS BROADCAST: the daemon writes ONE kill record (pid, the process's BASE NAME, RSS, age, the pressure readings that triggered it, and the reason — with any project path in the command line REDACTED, per the channeling invariant above) into the global-state dir in the `rotator-alert.json` shape, and `dispatch.py` surfaces ONE DESCRIPTIVE drift line per session on its next heartbeat fire — never an imperative instruction, never a bare `@name`. The payload is host-level and identical for every project, which is what makes it legal. (8) The kill record is ALSO written into the AFFECTED PROJECT's findings ledger for the audit trail, with the consequence leading so the 120-char cap truncates the least important tail. (9) Every kill is logged to `daemon.log` with the full command line, RSS, age and the readings that triggered it, in the shape `task_memory_guard` already uses. (10) The whole chore is OPT-IN and OFF BY DEFAULT, and the opt-in is a single documented plugin option; the option's absence must leave the host exactly as it is today.

THE MEASUREMENTS THAT MUST BE TAKEN BEFORE THE KILL PATH SHIPS, because the 2026-10-20 incident's own facts are not yet established. (a) What a swap-exhausted macOS host looks like in `vm_stat` and `vm.swapusage` at each stage, so the CRITICAL threshold is calibrated on a measured curve and not on a guessed number. (b) Whether freeing ONE process is enough to avert the kernel panic, or whether a drip of one-kill-per-beat is too slow against a 90-second watchdog — the 2026-10-20 episode was diffuse (19.8 GB across 986 processes), and if a single kill cannot avert the panic, the guard's value is in the EARLY WARNING, not the kill, and the card must say so honestly rather than claim a prevention it cannot deliver. (c) Whether a Claude-attributable process that is a USER'S OWN WORK (a dev server, a `pytest` run, a `vite` build started inside a session) can be told apart from a runaway — because on this host `alst` (4.5 GB) and `rust-analyzer` (1.4 GB) are both descendants of a `claude` session and both are legitimate work in progress. THIS IS THE OPENEST QUESTION IN THE CARD: the positive shape allowlist must exclude them, and how to exclude a legitimate user process by shape is not yet solved.

NEXT ACTION: read `scripts/lib/state.py`'s `parse_ps_table` / `process_ancestry` / `is_claude_command` / `claude_ancestor_pid` and `scripts/lib/memory_guard.py`'s `select_victim` / `kill_process` / `ProcRow` in full; read `scripts/lib/rotator_alert.py`'s `drift_parts` and `scripts/dispatch.py::_phase_rotator_alert` to fix the broadcast shape; then MEASURE (a) and (b) above on this host before writing the kill path, and put the CRITICAL threshold's measured curve in front of the owner with the readings beside it.

## ⏵ STATE — READ THIS FIRST ON RESUME (authoritative; supersedes the body) — 2026-10-20

**2026-10-20 18:40 — THE CHORE IS BUILT AND GREEN. IT IS DEFAULT-OFF AND HAS NEVER BEEN EXERCISED ON A REAL KILL.** The card's open question (how to tell an agent's runaway from the user's own work) is SOLVED BY MEASUREMENT, not by reasoning, and the answer is the ENVIRONMENT SIGNAL: a process whose own environment carries CLAUDECODE / CLAUDE_PROJECT_DIR / CLAUDE_PLUGIN_DATA / CLAUDE_CODE_SESSION_ID / CLAUDE_CODE_CHILD_SESSION was started by an agent, because a user typing at a shell prompt inherits a shell environment that has none of them. The signal SURVIVES REPARENTING, which is why it and not ancestry alone is the primary channel: measured on this host, `alcore serve` had ppid=1 and still carried three of the variables, and an abandoned watcher is by definition a reparented process. Ancestry is kept as a second, weaker signal and is necessary but not sufficient.

WHAT IS ON DISK: scripts/lib/runaway_guard.py (the pressure probe + the selection truth table), scripts/lib/runaway_alert.py (the daemon->session broadcast channel), tests/test_runaway_guard.py (17 tests), and the daemon chore `task_runaway_guard` in scripts/daemon.py registered in BOTH the Task registry and harness_backend.GLOBAL_CHORES (tests/test_harness_backend.py asserts the two match name-for-name, so both were needed). The dispatch phase `_phase_runaway_alert` prints one drift line per kill, ahead of the summary-hold gate.

THE PROBE SEES WHAT FREE MEMORY CANNOT. Measured live on this host after the build: swap 8695 MB in use with free memory at 32961 MB, and the state read ELEVATED. A free-memory-only probe would have called that host HEALTHY. That is the exact blind spot of the 2026-10-20 panic ('Compressor Info: 100% of segments limit (BAD), 69 swapfiles') and the reason the probe reads swap, the swapfile count and the compressor as well. The swapfile COUNT is None on this host (vm.swapinfo does not exist on this macOS) and is reported as '?' — an unknown reading never pushes the state UP, because 'critical' arms the kill path.

EVERY SAFETY CLAUSE IS MUTATION-VERIFIED, and three of the six mutations SURVIVED THE FIRST ROUND. That is the finding worth keeping. The interactive-claude, forbidden-client and protected-pid tests all passed with their clause DELETED, because with the shipped allowlist those commands match no runaway SHAPE, so the shape clause refused them and the test proved nothing. The fix was to WIDEN the allowlist inside those three tests to a pattern the target DOES match, which makes the clause under test the only thing that can refuse it. The rule this teaches is the one TRDD-03G3CSUU has now learned ten times: a test that cannot fail against its defect is worse than no test, and the way to know is to delete the clause and watch the test stay green.

THE MEASURED BEHAVIOUR ON THE LIVE HOST, which is the real proof the shape is right: with the age gate at its shipped 3600 s the guard selected NO victim, and the only shape-matching processes on the host were 56-second-old children of a live session. With the age gate set to 0 it selected `claude plugin update` — 288 s old, i.e. a plugin update that was RUNNING. The age gate is what protects live work from the kill path, and it is load-bearing, not a formality.

WHAT IS STILL OPEN. (1) The chore has never performed a real kill. The opt-in switch is CLAUDE_PLUGIN_OPTION_RUNAWAY_GUARD_ENABLED and it is OFF; the owner must set it. (2) The thresholds (MIN_FREE_MB, SWAP_USED_MB, SWAPFILES, COMPRESSOR_PCT) are defaults, not measured against a real exhaustion curve — the card's measurement (a) is still open. (3) The broadcast has been exercised in-process but never through a real daemon->session hop. (4) TRDD-C8SALZOO records the owner's directive that janitor chores must YIELD to host pressure, and it names the anti-deadlock requirement this chore must satisfy: the runaway-kill beat is EXEMPT from that gate, because it is the mechanism that ENDS the pressure. (5) The advisor's original open question about excluding a user's own dev server is now answered by the shape allowlist (a dev server matches no shape), and the dev server measured on this host is correctly refused.

NEXT ACTION: enable the chore on this host with a deliberately conservative threshold, exercise it against a REAL runaway the owner agrees to sacrifice, and confirm the kill is broadcast to a live session as one drift line. Then measure the exhaustion curve for the thresholds.

## Notes and lessons learned

2026-10-20 18:40 — THE CHORE IS BUILT, AND THE LESSON IS ABOUT THE TESTS, NOT THE CODE. Three of the six safety mutations SURVIVED the first round: the interactive-claude clause, the forbidden-client clause and the protected-pid clause could each be DELETED from the truth table and every test still passed. The cause is the same shape every time and it is worth stating precisely: the runaway-SHAPE allowlist is checked BEFORE the safety clauses, so any process that matches no shape is refused by the shape clause regardless of whether the safety clause exists. The three commands in question (a bare `claude`, `codex --serve`, `python3 scripts/daemon.py`) match no shipped shape, so the tests were asserting the shape allowlist three times over while the rule they claimed to test did nothing. THE FIX, and it is the generalisable part: a test of a safety clause must make that clause the ONLY thing that can refuse its subject, and the way to do that is to WIDEN the allowlist inside the test to a pattern the subject DOES match. All three tests now monkeypatch rg.RUNAWAY_SHAPES to add exactly such a pattern, and all three fail when their clause is deleted. A test that cannot fail against its defect is worse than no test — and here the tests were not merely weak, they were GREEN against a guard that had lost three of its six safety clauses, which is the most dangerous state a safety suite can be in. THE OTHER FINDING, on the attribution design: the ENVIRONMENT SIGNAL is what separates an agent's runaway from the user's own foreground work, and the card could not solve it by reasoning because the answer is not a shape, it is an INHERITANCE property — an agent's child inherits the agent's environment (which carries CLAUDECODE / CLAUDE_PROJECT_DIR / CLAUDE_PLUGIN_DATA / CLAUDE_CODE_SESSION_ID), while a command the user typed at a shell prompt inherits a shell environment that carries none of them. The signal also SURVIVES REPARENTING, which is decisive: an abandoned watcher has ppid=1 and no claude ancestor, so ancestry alone misses exactly the class the janitor was built for. MEASURED on the owner's host: `alcore serve` had ppid=1 and still carried three of the markers. THE PROBE'S VALUE, measured live after the build: the host had swap 8695 MB in use with 32961 MB free, and the state read ELEVATED where a free-memory-only probe would have read HEALTHY — which is the exact blind spot of the panic that motivated the card.
