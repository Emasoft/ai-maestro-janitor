### ⏵ SESSION ADDENDUM — 2026-06-11 (ROOT CAUSE of "rotator let a 429 happen instead of rotating" + hotpatch)

**Incident:** the live account (emanuele) climbed to 7d=97%, the rotator correctly flagged it
"exhausted" every 60s, but logged *"no alternate is healthy + below safe threshold — all paid
accounts maxed; waiting for a window to reset"* and never rotated → hard 429s → the new Claude
Code rate-limit MENU froze the session → the user had to rotate manually. The "maxed" alternate
(fmuaddib) was actually FRESH at 5h=3% 7d=60%.

**ROOT CAUSE (verified, not theorised):** the alternate's SLOT access token was **expired**, so
`cmd_auto`'s candidate probe `usage_request(b)` returned non-200 ("err") and the loop did
`continue` → excluded the only (fresh) alternate → `select_drain_first([])` → "all accounts
maxed" deadlock. The slot should have been kept fresh by `_keepalive_refresh`, but the **running
daemon is v0.6.1 (tag a3cfe94, 2026-06-04) which PREDATES the CF-1010 fix `6fdbeaa` (2026-06-09)**.
v0.6.1's `refresh_oauth_token` sends NO `User-Agent` on the token POST → Cloudflare 403 "error
code: 1010" → **the keepalive silently fails for EVERY slot** → all alternates inexorably lapse →
deadlock. The fix already exists in source (`6fdbeaa`) but sits in the 104 UNPUSHED commits — it
never shipped because the **publish is CPV-blocked** (same block, biting the rotator).

**IMMEDIATE FIX APPLIED + VERIFIED (2026-06-11):** hot-patched the running cached file
`~/.claude/plugins/cache/.../0.6.1/scripts/oauth_rotator/rotator.py` `refresh_oauth_token` to add
`"User-Agent": "claude-account-rotator"` (backport of `6fdbeaa`; backup
`rotator.py.pre-cf1010-hotpatch.bak`). Proof it works: `ROTATOR_KEEPALIVE_AHEAD_H=999 … tick`
logged `keepalive: refreshed emanuele.sabetta@gmail.com` (a refresh that would have CF-1010'd
before). Both slots now `refresh=yes`. The daemon subprocesses `_HERE/oauth_rotator/rotator.py`
fresh every 60s (`task_oauth_rotator_tick`, daemon.py:390), so it picked up the patch with NO
restart. The auto-updater won't clobber it (latest *published* is also 0.6.1 → update is a no-op);
when v0.6.2+ publishes it carries `6fdbeaa` natively and the daemon auto-rolls.

**DURABLE FIX:** ships automatically on the next CPV-unblocked janitor publish (source already has
`6fdbeaa`).

**HARDENING — DONE 2026-06-11 (this session, UNPUSHED — rides the same publish):** `cmd_auto`'s
candidate loop now does **refresh-on-err**. When an alternate's usage probe returns non-200 AND
non-429, the slot is `refresh_oauth_token`'d, healed back into the keychain (`write_slot`, fail-soft
on a locked keychain — keeps the fresh token in-memory), and re-probed BEFORE exclusion. So a single
stale access token can never again deadlock rotation even if the keepalive has a gap (the exact
2026-06-11 failure). 429 is deliberately NOT refreshed (the account is maxed, not the token expired —
a refresh would not help) and a slot whose refresh grant fails (setup-token / dead chain) is still
excluded. 3 focused tests added to `tests/test_oauth_rotator.py`
(`test_cmd_auto_refreshes_expired_alternate_before_excluding` / `…_does_not_refresh_maxed_429_alternate`
/ `…_excludes_alternate_when_refresh_fails`); 118 rotator-suite tests pass, ruff clean.
RESIDUAL (noted, not yet done): the refresh-on-err net covers the usage-probe-error exclusion (the

### The architecture — it is a TWO-HALF problem (do NOT conflate them)
Per the consolidated report: **no single project solves the whole crux; never
try to automate the login.**

- **TRANSPORT half (get past Cloudflare + Google SSO/2FA) = HUMAN, once per
  account.** A human logs in ONCE (lasts ~weeks) into the account's own clean,
  real-Chrome persistent profile. headless / automation-flagged browsers
  (Playwright/CDP/dev-browser) are **BLOCKED-BY-CLOUDFLARE** on the claude.ai
  login + Google pages — VERIFIED, repeatedly. Tool already built:
  `~/.claude/account-rotator/open-login.sh <email>` (clean Chrome, NO automation
  flags) → human logs in + Cmd+Q → `check-login.sh <email>` confirms a persistent
  `sessionKey`. Model the handoff on Agent-OS-main `login_handoff.py`
  (detect → WAIT_FOR_USER → persist → resume).
- **OAUTH-PROTOCOL half (renew the token) = AUTOMATED, on an ALREADY-SEEDED
  profile.** Automation REUSES the seeded profile (the `sessionKey` cookie skips
  CF + 2FA) → `claude.ai/oauth/authorize` → click **Authorize** → capture
  `code#state` → PKCE exchange → store. Reference: claude-login-automation
  `auth.ts`. Steady-state keepalive = pure-HTTP `grant_type=refresh_token`
  (claude-rotate `oauth.py`), NO browser.

**Renewal precedence:** PRIMARY = refresh-token grant (no browser, any slot that
HAS a refresh token). BOOTSTRAP / rare FALLBACK = seed-via-human-clean-Chrome
THEN automate-the-Authorize-click. The browser is needed ONLY to give a
setup-token slot its first refresh token, or to recover a dead refresh chain.

## Design (token lifecycle = 3 tiers)

1. **Access token (~8h)** — refresh via pure HTTP `grant_type=refresh_token`
   POST to the token endpoint. NO browser. This is "keepalive".
2. **Refresh token** — rotates on each refresh; proactively refreshing the IDLE
   slot before expiry keeps the chain alive indefinitely so Tier 3 never fires.
   HARD INVARIANT: keepalive refreshes ONLY the idle slot, NEVER the account
   currently loaded live (Claude owns the live one — double-refresh = rotation
   desync = logout).
3. **Full re-auth (rare)** — the "click Authorize on claude.ai" consent flow.
   Only needed if the refresh chain breaks. Browser-based.

Rotation shapes (linchpin still UNVERIFIED — see open questions):
- best case: a running `claude` re-reads the keychain per request, so the
  launchd agent swaps the slot and the next heartbeat-cron turn continues on
  the new account with no restart.
- fallback: relaunch `claude --continue`/`--resume` (same session preserved).

## VERIFIED 2026-05-28 (binary 2.1.153 + official docs)

Static analysis of the Claude Code Mach-O binary
(`~/.local/share/claude/versions/2.1.153`) plus the official docs
(`code.claude.com/docs/en/env-vars.md`, `.../llm-gateway.md`) resolved the
open mechanics:

1. **Auth source precedence** (`getAuthTokenSource`/`ny`): `ANTHROPIC_AUTH_TOKEN`
   → **`CLAUDE_CODE_OAUTH_TOKEN`** → CCR file → apiKeyHelper → profile →
   **claude.ai keychain blob** (`d9`) → none. The env token *takes precedence
   over the keychain* AND is read at process start — so it PINS one account for
   the process lifetime. Therefore the live overnight session must rely on the
   KEYCHAIN (mutable + re-read live), NOT on `CLAUDE_CODE_OAUTH_TOKEN`.
2. **Keychain re-read linchpin — RESOLVED (best case holds on macOS).** The
   OAuth blob is memoized (`d9`/`QZ` with `.cache`), but the cache-guard `mt1()`
   `stat()`s `~/.claude/.credentials.json` and, when it is **absent (true on
   macOS — keychain is the store)**, the `catch` branch clears the cache on
   *every* call. `mt1()` is awaited at the top of the refresh-check
   (`checkAndRefreshOAuthTokenIfNeeded`→`Qz8`) on the request path, so a running
   `claude` re-reads the keychain and a swapped credential is adopted on the
   next turn — **no restart**. Verified `.credentials.json` is absent on this host.
3. **`/api/oauth/usage` detector (the trigger breakthrough).** The binary's
   `fetchUtilization` GETs `https://api.anthropic.com/api/oauth/usage`; a live
   probe returns `{five_hour:{utilization,resets_at}, seven_day:{...},
   seven_day_sonnet/opus:{...}, extra_usage:{...}}`. Utilization is a 0-100
   percent. This is **zero inference cost** — so the rotator polls it to switch
   PROACTIVELY at ≥95% before a hard 429, instead of probing inference or
   parsing REPL state.
4. **`claude setup-token`** runs the OAuth flow and PRINTS a **1-year** access
   token ("you won't be able to see it again"; "export CLAUDE_CODE_OAUTH_TOKEN=").
   It is a mint-and-print, not a keychain write — capturing the 2nd account this
   way does not disturb the live session.
5. **Canonical prod config** (`tZq`), confirming the rotator constants:
   `TOKEN_URL=https://platform.claude.com/v1/oauth/token`,
   `CLIENT_ID=9d1c250a-e61b-44d9-88ed-5944d1962f5e`,
   `ROLES_URL=https://api.anthropic.com/api/oauth/claude_cli/roles`,
   refresh scopes = `user:profile user:inference user:sessions:claude_code
   user:mcp_servers user:file_upload`, beta header `oauth-2025-04-20`.
6. **LLM gateway is irrelevant to Max rotation** — it is the API-key/gateway
   billing path (LiteLLM/Bedrock/Vertex), not OAuth-subscription auth.

### Cookie-vs-OAuth lifetime monitor + the never-coincide invariant (user requirement)

The DANGER: if a profile's cookie expires at the same time that account's OAuth
is exhausted, there's no working path to recover (and no usable Claude Code
session to run the refresh from). The INVARIANT: always refresh cookies EARLY —
while OAuth is still healthy — so cookie-death never coincides with OAuth-death.

- BUILT: `~/.claude/account-rotator/lifetime-status.sh` — per account, compares
  cookie/session lifetime (profile `sessionKey` expiry) vs OAuth lifetime (slot
  `refreshToken` presence + `expiresAt`). Verdicts: LOGIN NEEDED / REFRESH SOON
  (cookie < `COOKIE_REMIND_DAYS`, default 7) / RE-CAPTURE (setup-token <
  `SETUP_REMIND_DAYS`, default 30) / ok. When action is due it confirms OAuth is
  still healthy ("safe window") so the user can always act; if no account is
  healthy it escalates to URGENT (login is a fresh sign-in, doesn't need the old
  cookie). Verified live: both accounts → LOGIN NEEDED (profiles empty), OAuth
  healthy 2/2.
- **BUILT — the proactive reminder (the "janitor reminds me" piece):**
  `scripts/detectors/oauth-cookie-reminder.py` (plugin) + roster entry in
  `dispatch.py` (`oauth-cookie-reminder`, 6h cadence,
  `CLAUDE_PLUGIN_OPTION_OAUTH_COOKIE_REMINDER_INTERVAL`). On the per-session
  heartbeat it compares each account's cookie vs OAuth lifetime and emits a
  REFRESH-SOON reminder BEFORE a cookie expires while OAuth is healthy.
  OPT-IN BY PRESENCE: silent no-op unless a rotator home with a state.json
  exists (`CLAUDE_ROTATOR_HOME` / `~/.claude/account-rotator` /
  `$CLAUDE_PLUGIN_DATA/oauth-rotator`) — never fires for janitor installs
  without the rotator. Machine-scoped daily dedupe (seen-file in the rotator
  home) keeps it to ~one reminder/day even though the heartbeat fires it in
  every project. Logic mirrors the local `lifetime-status.sh`. Tests:
  `tests/test_oauth_cookie_reminder.py` (5 cases: healthy→silent,
  near-expiry→remind+safe-window, no-session→login-needed, setup-token<30d→
  re-capture, no-rotator→opt-in-noop). ruff+mypy clean; verified live (both
  accounts healthy → silent; forced threshold → emits). This is the surfacing
  half of P2 (the daemon does mutations; the per-session detector does the
  user-facing reminder).
