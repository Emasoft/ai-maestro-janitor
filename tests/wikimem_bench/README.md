# wikimem retrieval benchmark

Harness `scripts/wikimem_bench.py` · ground truth `queries.json` (shared) · **two** frozen
corpora, each with its own committed baseline:

| corpus | baseline | what it measures |
|---|---|---|
| `tests/fixtures/wikimem-bench-conformant/` | `baseline-conformant.json` | **PRIMARY.** Retrieval over a corpus in the form the spec MANDATES (`underscore_joined` key-phrases). This is the number to improve. |
| `tests/fixtures/wikimem-bench/` | `baseline.json` | **LEGACY.** The same corpus in the pre-migration comma form, which `atom-dropped-props` now rates CRITICAL. Kept so a change cannot quietly make NON-CONFORMANT input worse, and so every historical measurement stays comparable. |

Run them as:

```bash
uv run scripts/wikimem_bench.py --check --allow-dropped-keywords           # legacy
uv run scripts/wikimem_bench.py --check \
  --corpus tests/fixtures/wikimem-bench-conformant \
  --baseline tests/wikimem_bench/baseline-conformant.json                  # primary
```

**`--allow-dropped-keywords` is mandatory for the legacy run** (issue #119). The harness refuses
to score any corpus `memgrep lint` reports an `atom-dropped-props` finding for: on such a corpus
`hit@1/3/10` cannot tell "the ranker missed it" from "nothing could ever have retrieved it" — a
truncated atom silently depresses the baseline instead of being reported. The legacy corpus below
is the ONE deliberate exception; the primary corpus must never need the flag.

Set `MEMGREP_BIN=/path/to/target/release/memgrep` to measure a build **before** installing it —
otherwise every run silently scores whatever is on `PATH` and reports the old binary's numbers as
the new one's improvement (WM-BENCH-07).

## The two-corpus result, and why the legacy baseline was allowed to drop

The keyphrase-aware scorer was measured as a 2×2 against both corpora and both binaries:

| corpus | scorer | hit@1 | hit@10 | MRR |
|---|---|---|---|---|
| legacy (broken) | pre-tier | 21.7% | 65.2% | 0.3964 |
| legacy (broken) | tiered | 21.7% | **60.9%** | **0.3855** |
| conformant | pre-tier | 95.7% | 100% | 0.9783 |
| conformant | tiered | **100%** | 100% | **1.0000** |

The legacy drop is ONE query, and it is the correctness fix working rather than a regression.
`"list after put is stale"` targets an atom whose *third* keyword segment is exactly that phrase —
the segment the broken parser deletes. The old scorer still "found" it at rank 5 **because `list`
is a substring of `listing`** in the one segment that survived. That was an accidental collision,
not a symptom match; token-aware matching (WM-SCORE-06) removes it. On the conformant corpus the
same query hits **rank 1**.

So: the tiered scorer trades away false hits that only exist on input the linter now rejects, and
buys a **perfect MRR** on input the spec mandates. The legacy baseline was re-captured to record
that trade explicitly — never to make a failing gate pass.

**Absolute token counts are path-length dependent.** The same corpus measured at a long temp path
costs more per query than at a short repo-relative one (observed: 343.5 vs 283.7). Compare runs at
the SAME corpus path; never compare token counts across corpora at different depths.

Until 2026-07-26 the dominant cause was that a page ROW printed the corpus path; that is fixed
(the row now prints the page's `name:` — WM-RCL-06b). Paths still reach the output through the
second HOP, which prints the resolved page/atom path an editor needs, so the dependence is
reduced, not removed — and the guidance above is unchanged.

The corpus dir holds **memory pages and nothing else** — this README lives here rather than beside
them because any `.md` inside that directory is parsed as a memory page: it would be linted as one
and could be returned as a retrieval candidate, quietly skewing the very numbers being measured.
It did, until it was moved (mean cost fell 443.5 → 441.4 tokens/query on the move alone).

**Do not "fix" the keyword syntax in `wikimem-bench/` (the LEGACY corpus).** Its pages are
authored in the comma-separated multi-word form the live corpus used, which the parser truncates
at the first comma (TRDD-DO6X4ZF8, plan Phase 1.3). That truncation is the thing under
measurement. Normalising those files by hand would erase the very signal the benchmark exists to
detect, and would silently turn the baseline into a lie. The repaired form already exists as the
separate `wikimem-bench-conformant/` corpus — generated by running
`scripts/wikimem_migrate_keywords.py --apply` over a COPY, never by editing the legacy pages.

Frozen on purpose: the live corpus changes weekly, so benchmarking against it would make every
run incomparable to the last — the opposite of a regression instrument. Pointing the harness at a
live corpus with `--corpus <path>` is fine for a SPOT CHECK and never gates. (This paragraph used
to name a `--live` flag that has never existed; the spec-drift check caught the same phantom in
the spec. A flag named in prose is a promise someone will eventually try to keep.)

Content is generic software-engineering material (connection pools, TLS chains, cron drift). It
deliberately shares no subject matter with the real project corpus, so a page here can never be
mistaken for, or drift against, a real memory.

## Baseline moves, and why each was allowed

A baseline may only move on a DOCUMENTED trade — otherwise "re-capture it" becomes the universal
way to make a regression disappear.

| date | corpus | change | why it was allowed |
|---|---|---|---|
| 2026-07-26 | legacy | hit@10 65.2% → 60.9% | the tiered scorer stopped substring matching (`list` inside `listing`) scoring accidental hits on the pre-migration corpus. A correctness fix that LOWERS a metric on a deliberately-broken fixture; the conformant corpus is the one that reports the truth |
| 2026-07-26 | both | 283.7 → 272.0 and 185.4 → 174.3 tokens/query | a PAGE row's locator became the page's `name:` instead of its path (TRDD-YBOZW3ES). Accuracy fields are byte-identical in both baselines — only token counts moved, and downward |

**The fixture UNDERSTATES that second saving by roughly 8×, and the reason matters.** These corpora
sit at a short repo-relative path (`tests/fixtures/…/pool-exhaustion.md`, ~52 chars), so dropping
it saves ~9 tokens per page row. A real memory root is an ABSOLUTE path around 126 chars, where
the same change saves ~90 — measured at ~80–110 tokens/query across the two live corpora.

So the benchmark is a faithful REGRESSION detector and a conservative estimate of absolute cost:
the fixture's own path length is a hidden parameter of every token figure it reports. Do not quote
its per-query number as the real-world cost, and do not "improve" it by relocating the corpus —
that would move the number without changing anything an agent experiences.
