# host-resource-pressure




^ATOM-AXIF-X3GR [desc: "A 2026-10-20 macOS kernel panic was swap/compressor exhaustion, not one app: the panicked task is whoever was running when the watchdog window expired.", keywords: mac_kernel_panic watchdog_timeout_no_checkins_in_90_seconds PerfPowerServices compressor_at_100_percent_of_segments_limit 69_swapfiles swap_space_OK panic_cpu_2_caller which_task_panicked mac_crashed_under_memory_pressure the_mac_crashed the_kernel_panicked watchdog_timeout, type: project, trdd: TRDD-5G66S0HK, ocd: 2026-10-20, lmd: 2026-10-20]

**THE PANIC (measured 2026-10-20, on a macOS host of the ordinary desktop size).** The kernel panicked: `panic(cpu 2 caller ...): watchdog timeout: no checkins from watchdogd in 90 seconds`. The panic log carried its own diagnosis: `Compressor Info: 32% of compressed pages limit (OK) and 100% of segments limit (BAD) with 69 swapfiles and OK swap space` — the COMPRESSOR hit its SEGMENT limit. The panicked TASK was `PerfPowerServices`: that is the thread that happened to be running when the 90-second watchdog window expired, NOT the cause of the starvation. Naming it as the cause is the first mistake to avoid. [^2]


^ATOM-XSXS-Z5DW [desc: "The crash happened at 10:41:37 per the panic log's own Calendar: epoch; the diagnostic file's 11:33 mtime is only when CrashReporter wrote it.", keywords: panic_log_mtime_is_not_the_crash_time CrashReporter_writes_the_file_later Calendar_epoch_field_in_the_panic_log crash_happened_at_10_41_37 reboot_27_seconds_later kern.boottime_cross_check read_the_crash_time_from_the_file_timestamp why_is_the_timeline_an_hour_off diagnostic_file_timestamp_vs_event_time panic_log_epoch_field, type: project, trdd: TRDD-5G66S0HK, ocd: 2026-10-20, lmd: 2026-10-20]

**THE CRASH TIME IS NOT THE FILE TIMESTAMP.** The panic file mtime was 11:33, but the crash happened at 10:41:37 — the panic log carries its own `Calendar:` epoch field, and the reboot followed 27 seconds later. The mtime is when CrashReporter WROTE the file. Reading the crash time from the file timestamp puts the investigation an hour off, which is long enough to mis-attribute the whole episode. Cross-check the `Calendar:` epoch against `kern.boottime`. [^1]


^ATOM-3UMC-3NT4 [desc: "2026-10-20 jetsam snapshot: a CENSUS of hundreds of processes holding ~20 GB RSS across many categories — claude sessions, node, AI clients renderers, WindowServer, iTerm2 — exhaustion, not one app.", keywords: JetsamEvent_ips_snapshot hundreds_of_processes_holding_20_GB_RSS concurrent_claude_cli_sessions node_processes other_ai_clients_renderers WindowServer_and_iTerm2 first_line_is_JSON_metadata the_cause_was_memory_exhaustion_not_one_application jetsam_memory_snapshot_format who_was_consuming_the_ram a_census_not_a_culprit, type: project, trdd: TRDD-5G66S0HK, ocd: 2026-10-20, lmd: 2026-10-20]

**THE CAUSE WAS MEMORY EXHAUSTION ACROSS THE WHOLE HOST, NOT ONE APPLICATION.** The jetsam snapshot from the same episode (a macOS `JetsamEvent-*.ips` file — its first line is JSON metadata and its remaining lines are a JSON payload) recorded a process census in the HIGH hundreds of processes holding close to 20 GB RSS, spread across MANY categories at once: several concurrent `claude` CLI sessions, dozens of `node` processes, other AI clients' renderers, and the window server and terminal. No single process caused it; the aggregate did. The lesson is the SHAPE — a census, not a culprit — and the exact per-category figures belong to the host they were measured on, not here.


^ATOM-LQ1M-WDCY [desc: "memory_guard.py measures free memory only and host-load.py load average only; nothing in the janitor reads vm.swapusage or compressor occupancy, so the crash was invisible to it.", keywords: memory_guard_measures_FREE_MEMORY_ONLY parse_vm_stat_Pages_free_plus_Pages_speculative DEFAULT_MIN_FREE_MB_1024_MiB host_load_detector_bar_is_cores_x_4 nothing_reads_vm.swapusage compressor_occupancy_is_never_read the_janitors_probe_could_not_see_it free_memory_736_MB_after_reboot the_existing_guard_WAS_firing wrong_quantity_the_probe_read, type: project, trdd: TRDD-5G66S0HK, ocd: 2026-10-20, lmd: 2026-10-20]

**THE JANITOR PROBE COULD NOT SEE IT — the load-bearing gap.** `scripts/lib/memory_guard.py` measures FREE MEMORY ONLY: `parse_vm_stat` sums `Pages free` + `Pages speculative` and compares the result to `DEFAULT_MIN_FREE_MB` = 1024 MiB. `scripts/detectors/host-load.py` measures LOAD AVERAGE only (bar = cores x 4). NOTHING in the janitor reads `vm.swapusage` or the compressor occupancy — a search for `swapusage` / `occupied by compressor` across `scripts/` returns nothing but unrelated false positives. The panic's own diagnosis was a COMPRESSOR-AT-SEGMENT-LIMIT condition with 69 swapfiles, so on a host with RAM to spare the machine died under SWAP exhaustion while free memory still looked survivable: the one probe that existed was reading the wrong quantity. Measured after the reboot, `free_memory_mb()` returned 736 MB — BELOW the 1024 floor, so the existing guard WAS firing — and it could see neither the swap nor the compressor. [^3]


^ATOM-W8MF-T5VO [desc: "The janitor's own daemon log already held the warning: ps timed out after 10s and a 9.7s security op — a process listing could not complete — yet nothing treats ps timeout as host pressure.", keywords: ps_timed_out_after_10s rotator_ps_eo_args_timed_out assuming_Claude_is_running_fallback safe_storage_SLOW_security_op_9667ms system_daemon_runaway_subprocess_timed_out_ps the_pre_crash_signal_was_in_our_own_logs ps_timeout_is_not_treated_as_host_pressure the_machine_was_already_starved process_listing_could_not_complete the_janitor_did_not_warn_before_the_crash, type: project, trdd: TRDD-5G66S0HK, ocd: 2026-10-20, lmd: 2026-10-20]

**THE PRE-CRASH SIGNAL WAS ALREADY IN THE JANITOR'S OWN LOGS.** The daemon logged `rotator: ps -eo args= timed out after 10s - assuming Claude is running` and `[safe-storage] SLOW security op: 9667ms (timeout 5s, TIMED OUT)` — a plain `ps` could not complete in 10 seconds. A detector later logged `system-daemon-runaway subprocess timed out after 10.0s: ps`. The host was already so starved that a process listing exceeded its own timeout, and NOTHING in the janitor treats "ps timed out" as a host-pressure signal. That timeout is the earliest machine-readable warning available, and it is currently read as a benign "assume Claude is running" fallback.


^ATOM-XBO1-GV5X [desc: "A new kill authority needs its own card, opt-in and default; it cannot be folded into the Tier-1 guard, whose six janitor-only signatures are the safety contract's load-bearing clause.", keywords: JANITOR_WORKLOAD_SIGNATURES_six_shapes Tier-1_safety_contract_load-bearing_clause Tier_2_killing_non_janitor_processes_NOT_implemented Decision_1_no_code_path_or_enabling_flag separate_kill_authority_own_opt_in_own_default two_kill_authorities_can_race disjoint_protected_pid_sets memory_guard_must_not_absorb_the_fix the_fix_needs_its_own_TRDD kill_only_what_Claude_Code_caused, type: project, trdd: TRDD-5G66S0HK, ocd: 2026-10-20, lmd: 2026-10-20]

**THE FIX IS A SEPARATE KILL AUTHORITY, and the existing guard must NOT absorb it.** `memory_guard.py` confines kills to `JANITOR_WORKLOAD_SIGNATURES` (six janitor-spawned shapes) and makes every other `claude`-shaped command — the user's interactive session — categorically non-killable; the code calls that "the Tier-1 safety contract's load-bearing clause". `scripts/daemon.py::task_memory_guard` says in its own docstring that Tier 2 (killing non-janitor processes) "is NOT implemented — per Decision 1 it stays off the table without a fresh user sign-off; there is deliberately no code path or enabling flag for it". A new kill authority needs its OWN card (TRDD-5G66S0HK), its OWN opt-in, and its OWN default: it cannot ship default-off inside a default-on chore, and two kill authorities on one host with disjoint protected-pid sets can race each other.


^ATOM-7EF0-T3AE [desc: "Ancestry is necessary but insufficient: the interactive session is a descendant not an ancestor, and launchd attribution makes the janitor's own daemon and the Codex daemon kill candidates.", keywords: ancestry_is_necessary_but_not_sufficient claude_ancestor_pid_walk interactive_session_is_a_DESCENDANT_of_the_shell ancestor_protection_does_not_cover_it launchd_agent_attribution_is_self_killing com.ai-maestro-janitor.daemon_launchd_agent com.cblh.codex-app-server.plist path_or_environment_channel CLAUDE_PROJECT_DIR_CLAUDECODE_CLAUDE_PLUGIN_DATA processes_that_reparent_to_launchd, type: project, trdd: TRDD-5G66S0HK, ocd: 2026-10-20, lmd: 2026-10-20]

**THE ATTRIBUTION HAZARD — the part a future implementer will get wrong.** Ancestry (a process whose parent chain reaches a `claude` process) is NECESSARY but NOT SUFFICIENT, for two measured reasons. (a) The user's own interactive session is the LARGEST killable candidate on a loaded host, and it is a DESCENDANT of the user's shell — never an ancestor — so a "never kill a live session's ancestor" carve-out does not protect it. (b) Attributing by "started by a launchd agent a Claude Code plugin installed" is SELF-KILLING: the janitor installs exactly one launchd agent (`com.ai-maestro-janitor.daemon`), so that clause makes THE JANITOR DAEMON a kill candidate — and it sweeps in `com.cblh.codex-app-server.plist`, the Codex daemon the owner forbade touching. A path/environment channel (a command line referencing `~/.claude/`, `plugins/cache/`, or an environment carrying `CLAUDE_PROJECT_DIR` / `CLAUDECODE` / `CLAUDE_PLUGIN_DATA`) catches processes that outlive their session and reparent to launchd, which ancestry cannot. ^ATOM-7FYG-I6VC [desc: "Attribution proves relatedness, not kill-worthiness: a positive shape allowlist plus the age gate is required, or the rule degenerates to biggest-process-wins and kills rust-analyzer.", keywords: attribution_is_a_filter_never_a_kill_criterion positive_allowlist_of_runaway_SHAPES DEFAULT_RUNAWAY_ETIME_S_age_gate biggest_process_wins_is_what_Decision_1_refused alst_rust_binary_4_5_GB rust-analyzer_1_4_GB both_descendants_of_a_claude_session ancestry_alone_would_kill_a_users_IDE kill-worthiness_is_not_relatedness shape_allowlist_not_just_attribution, type: project, trdd: TRDD-5G66S0HK, ocd: 2026-10-20, lmd: 2026-10-20]

**ATTRIBUTION IS A FILTER, NEVER A KILL CRITERION.** "Attributable to Claude Code" proves RELATEDNESS, not kill-worthiness. A positive allowlist of runaway SHAPES among the attributed candidates is required — exactly as `JANITOR_WORKLOAD_SIGNATURES` embodies for janitor-owned workloads — plus the age gate `DEFAULT_RUNAWAY_ETIME_S`. Without it the rule degenerates to "biggest process wins", which is what Decision 1 refused. The measured hazard: on the loaded host, `alst` (a Rust binary at 4.5 GB) and `rust-analyzer` (1.4 GB) were BOTH descendants of a `claude` session and BOTH legitimate work in progress. Ancestry alone would have killed a user's IDE.



^ATOM-9TGU-DB4Z [desc: "A host-level kill record is only legal as an identical host-level payload like rotator-alert.json; it may carry pid, base name, RSS and age, never a project path or command line.", keywords: per_project_channeling_invariant_TRDD-X92VBFNF rotator-alert.json_host_level_payload _phase_rotator_alert_prints_one_drift_line no_project_path_in_the_broadcast no_command_line_in_the_broadcast base_name_RSS_age_pid_only full_command_line_stays_in_the_daemon_log drift_line_must_be_DESCRIPTIVE_never_imperative autonomous_readers_execute_imperative_status_lines TRDD-X92VBFNF_applies_to_kill_events, type: project, trdd: TRDD-5G66S0HK, ocd: 2026-10-20, lmd: 2026-10-20]

**THE BROADCAST MUST SATISFY THE PER-PROJECT CHANNELING INVARIANT (TRDD-X92VBFNF).** An automatic surface may carry information about EXACTLY the project it fires in. A kill event is about the HOST, so it is legal ONLY as a host-level payload identical for every project — the shape `rotator-alert.json` already uses (the daemon writes one file into the global-state dir; `scripts/dispatch.py::_phase_rotator_alert` prints one drift line per session). The consequence for the payload: it may name the pid, the process's BASE NAME, its RSS, its age and the pressure readings, but NOT a project path and NOT a command line carrying one — a command line like `pytest ~/Code/<project>/other-project/tests` would push one project's content into every other project's session. The full command line belongs only in the daemon's own log and in the affected project's ledger entry. Also: the drift line must be DESCRIPTIVE, never imperative, because this codebase has already been burned by imperative status lines being executed by autonomous readers.
