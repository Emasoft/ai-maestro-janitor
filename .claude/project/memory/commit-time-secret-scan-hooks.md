# commit-time-secret-scan-hooks


^ATOM-U38Y-QRHN [desc: "prepare-commit-msg and commit-msg run staged_secret_scan.py on the index and the message, so cherry-pick, rebase and --no-verify are scanned; a finding blocks", keywords: commit_blocked_by_secret_scan staged_secret_scan.py_scans_the_index_blobs git_hook_order_prepare-commit-msg_pre-commit_commit-msg pre-commit_does_not_run_on_cherry-pick_rebase_no-verify pre-merge-commit_hook_retired no-verify_no_longer_skips_the_secret_scan amend_compares_with_the_commit_being_amended secret_scan_exit_2_blocks_the_commit scan_inert_when_janitor_DATA_dir_absent_or_kill-switch_set why_a_hook_and_not_a_PreToolUse_guard secret_in_commit_message_reaches_git-cliff_changelog v1_blocks_never_rewrites_a_file, type: reference, trdd: TRDD-FNPDFZWU, ocd: 2026-11-19, lmd: 2026-11-19]

Owner order 2026-11-18 (TRDD-FNPDFZWU): the secrets shield must stop a secret from being committed, before git-cliff builds the changelog, because a secret in a commit reaches GitHub release notes and package metadata. Why git hooks and not a PreToolUse guard: `git add x && git commit` is one Bash call so a guard fires before the add, and `commit -a` and pathspec commits build their index inside git; only the hooks see what is committed. scripts/lib/staged_secret_scan.py writes each staged blob (read through the INDEX object ids, so a partly staged file is judged as committed) into a 0700 temp tree outside git and runs the shield scanner (scripts/shield_scan/scan.ts) with bun started in the plugin folder (a repo bunfig preload never runs, TRDD-6E2I17HN). A finding blocks unless its whole line already exists in the HEAD blob of the same path (so existing fixtures pass); the commit message has no baseline. Exit 2 (cannot run, incomplete scan, a text file over 64 MB) blocks too. Inert when the janitor DATA dir is absent or the kill-switch is set. v1 BLOCKS and never rewrites a file: a marker written into a working file cannot be restored and can overwrite uncommitted work. Hook placement (21c6e574): measured in scratch repos with marker hooks, pre-commit does not run on cherry-pick, rebase picks or commit --no-verify, and pre-merge-commit only on merge --no-ff, while prepare-commit-msg runs on all of them and a non-zero exit aborts each; so one hook, git-hooks/prepare-commit-msg, replaced pre-commit stage 0b and the pre-merge-commit hook (retired; core.hooksPath stays git-hooks so a stale .git/hooks/pre-merge-commit copy is not run), and git-hooks/commit-msg scans the message. Costs: --no-verify no longer skips the secret scan; --amend compares with the commit being amended, so a secret from an earlier unscanned commit passes the amend (the push-time range scan covers it). It runs after pre-commit, so stage 0 redaction of reports/ happens first. Gaps left: fast-forward merges and pulls run no blocking hook, am runs pre-applypatch, binary blobs are not scanned, a secret already in HEAD is not flagged. publish.py install_hook installs the hooks.


^ATOM-E5ZL-VUZ7 [desc: "pre-push and publish.py run staged_secret_scan.py --range before trufflehog, the release gate and git-cliff; .janitor-secret-allow exempts fake file values only, read from the index or tip commit", keywords: push_blocked_by_range_secret_scan publish_blocked_before_git-cliff_secret .janitor-secret-allow_entry_format_kind_path_line_sha256_blob_oid exempt_a_fake_secret_value allow_file_not_committed_exempts_nothing --print-allow-entries_REVIEW-ME_reason commit_message_secret_can_never_be_exempted secret_scan_range_remote..local_--not_--remotes exempted_findings_disclosure_count_new_entries pushed_commit_adds_its_own_allow_entry 17_range_findings_AWS_EXAMPLE_keys_exempted publish.py_stage_bump_secret_scan_order trufflehog_runs_after_range_scan, type: reference, trdd: TRDD-FNPDFZWU, ocd: 2026-11-19, lmd: 2026-11-19]

The commit-time scan misses commits that never ran it (cherry-pick, rebase picks, commit --no-verify before 21c6e574, fast-forward merges, am), so 3c79a953 (TRDD-FNPDFZWU increment 2c) added staged_secret_scan.py --range <rev-list args>: it scans every commit of the range, its message and every blob it adds or changes against its first parent, in one scanner run; findings name commit, path, line and kind, never a value. git-hooks/pre-push runs it on every pushed ref (remote..local, or local --not --remotes for a new ref or a remote sha this clone lacks) BEFORE trufflehog and the release gate; a secret or a scan that could not run blocks the push. scripts/publish.py runs it on <last release tag>..HEAD and on a git-cliff stdout preview of the notes BEFORE stage_bump, so a block leaves the tree as it was (by construction and a direct-call test; publish.main itself was not run), and scans the real CHANGELOG section and the gh release notes again as a safety net after the files are written. Allow file .janitor-secret-allow (repo root, tracked): exemptions for FILE findings only, four TAB-separated fields <kind> <path> line:<sha256 hex of the line text> or blob:<full git blob oid> <reason>; a finding with no line number can only be exempted by a blob entry; a malformed line makes the scan exit 2. It is read from the INDEX for a commit and from the TIP COMMIT of the range for push and publish, never from the working tree, so a list that is not committed exempts nothing. Messages, release notes and CHANGELOG text can never be exempted. A line: entry is only for a value judged FAKE (a real secret is rotated, then history rewritten); an unsalted line hash is acceptable because the entry exists only for a line already in a pushed blob; when that line leaves history its entry must go too. staged_secret_scan.py --print-allow-entries [--range ...] prints ready lines with the reason REVIEW-ME to be replaced by who judged the value fake and when. Every run discloses how many findings were exempted and how many by entries new since the base (publish.py forwards it on a passing scan too). A pushed commit that adds its own entry is disclosed, not refused (interim default put to the owner). First effect: the range scan blocked every push and publish of this repo until entries for 17 range findings were committed; all 17 were shape-checked without printing a value (AWS documentation EXAMPLE keys, a fake() fixture, short or placeholder values), then d7d18db4 added 14 line entries for 7 owner example values in the janitor-env-tools example files and test_envget.py, each present in two copies.

A fixture hygiene lesson of the same days: a test fixture that even looks like a secret (a 64-char base62 literal, a URL that carries a user name and password, an sk- key) trips ubs, the secret scanners and the privacy scan, so fixtures are built at run time (tests/_fake_secrets.b62 is a sha256-chained deterministic generator, 56b5b9b9) or from split pieces.
