# janitor-publish-pipeline — the `[G1b]` personal-address lint

^ATOM-M8YK-YILO [desc: "publish.py [G1b] blocks a push whose ADDED lines introduce a non-allow-listed e-mail address the same file did not already hold on the remote base ref; masked output; the gate scans its own tests", keywords: personal_e-mail_address_introduced G1b_personal-address_lint BLOCKED_personal_e-mail_address publish_blocked_on_an_email_address gmail_address_in_a_tracked_file redact_the_way_the_repo_already_does address_already_on_the_base_ref masked_address_f***@domain users.noreply.github.com_allowed example.com_allowed per-file_known_address_exclusion git_show_ref_path added_lines_only the_gate_flagged_its_own_test_file, type: project, trdd: TRDD-QW7K3M2V, ocd: 2026-09-02, lmd: 2026-09-02]

`scripts/publish.py` gate `[G1b] Personal-address lint` (2026-09-02, TRDD-QW7K3M2V, commits da471290/fb48d144/92af2072): after [G1] it diffs `<remote default ref>...HEAD` with `--unified=0` and scans ADDED lines only for an e-mail address whose domain is not allow-listed (`users.noreply.github.com`, RFC reserved doc domains .local/.test/.example/.invalid/.localhost, exact example.com/org/net, local parts noreply/no-reply) and that the SAME FILE did not already hold on the base ref (`git show <ref>:<path>`, per file — a repo-wide set would let an address living only in a frozen terminal card be pasted into any new file). A hit blocks the push and prints the address MASKED (`f***@domain`). It exists because three personal addresses already sit in 12 tracked files of this public repo since 2026-05-28 and the owner ruled: leave history alone, stop the bleeding (option 1). The gate's own test module must assemble every flaggable address at runtime around a split `@` and never spell one in a comment — the gate scans its own tests too. [^13]




^ATOM-GVS2-P6DK [desc: "[G1b]'s domain class swallows a trailing file extension, so an email-shaped PATH literal is read as a real domain and blocks the push even when its TLD is allow-listed", keywords: publish_blocked_on_a_path_that_is_not_an_email dot-invalid_is_allow-listed_but_the_publish_still_blocked email-shaped_filename_literal slot_json_filename_blocked_the_release G1b_flagged_a_path_not_an_address _EMAIL_RE_domain_swallows_the_file_extension RFC_2606_invalid_TLD_rejected_by_the_lint how_do_I_write_an_email-shaped_test_path split_the_local_part_into_a_variable address_lint_false_positive_on_a_filename, type: reference, ocd: 2026-09-03, lmd: 2026-09-03]

`_EMAIL_RE = [A-Za-z0-9._%+-]+@[A-Za-z0-9.-]+\.[A-Za-z]{2,}` (scripts/publish.py:909) is GREEDY on the domain and has no notion of a filename, so a path literal like `f"{slot}@invalid.json"` parses as domain `invalid.json` — which does NOT end with the allow-listed suffix `.invalid`, and blocks the push. The TLD being RFC 2606 reserved buys nothing: the extension is what the lint reads. The fix is to keep the `@` out of the joined literal — bind the local part to a variable (`_slot_b = "b@invalid"`) and interpolate it, because a bare `b@invalid` has no `\.[A-Za-z]{2,}` tail and therefore never matches the regex at all. Measured 2026-09-04 (publish 3.4.14, attempts #4 and #5). [^16] [^18]




^ATOM-DL17-5K5Q [desc: "CPV --strict step 4 flags an absolute /Users/<name>/ path anywhere in a tracked TRDD card or memory page as CRITICAL 'Private path leaked' and blocks the publish", keywords: publish_blocked_private_path_leaked CPV_strict_/Users/_in_TRDD_card absolute_home_path_in_design/tasks 18_CRITICAL_private_path private_path_leaked_CPV_strict absolute_path_in_memory_page grep_-rl_/Users/_before_publish genericize_path_before_publish TRDD_card_leaked_home_directory worker_report_path_pasted_into_card CPV_--strict_step_4_blocked RC_path-privacy_class, type: project, ocd: 2026-09-17, lmd: 2026-09-17]


publish.py's CPV --strict step 4 (RC path-privacy class) scans EVERY tracked file including design/tasks/*.md and .claude/project/memory/*.md for an absolute /Users/<name>/ (or other home-dir) path; pasting one from a worker report or tool-output snippet into a TRDD card or memory page raises a CRITICAL 'Private path leaked' finding per occurrence and blocks the push after lint/tests already passed. Measured 3.5.6 (2026-09-17): 18 CRITICAL across four TRDD cards, all sourced from pasted worker-report paths. Fix at write time: genericise to repo-relative, ~/, or <slug> before committing, and grep -rl '/Users/' over design/ and .claude/project/memory before running publish.py. [^19]

## Notes and lessons learned
[^13]: [id: ATOM-W9LC-3G7E, status: valid, desc: "A repo-scanning lint must be run over its own commit before landing; fixtures and comments are tracked lines too", keywords: "the_gate_flagged_its_own_test_file lint_blocked_the_commit_that_ships_the_lint test_fixture_contains_a_real-looking_email literal_gmail_address_in_tests self-tripping_gate split_the_at_sign_in_fixtures run_the_lint_over_origin/main_before_committing G1b_hits_in_tests/test_publish_personal_address_gate.py comment_spelled_out_an_address address_regex_matches_source_code", ocd: 2026-09-02, lmd: 2026-09-02] DO NOT write a flaggable literal (a gmail-style address) into the address gate's own tests or comments, BECAUSE [G1b] scans every ADDED line of every tracked file including its own test module — measured 2026-09-02: six hits from literal fixtures, then one more from a comment that spelled an address out, each would have blocked the publish shipping the gate. DO assemble every flaggable fixture at runtime around a split '@' (`f"{local}{AT}gmail.com"`) and run the two helpers over origin/main...HEAD before committing any lint that scans the repo.
[^16]: [id: ATOM-E2CQ-08HY, status: valid, keywords: "I_checked_the_gate_would_pass_but_it_blocked_anyway hand-wrote_a_regex_to_approximate_the_lint verified_the_mechanism_not_my_data phantom_hits_from_a_stub_known_for how_do_I_dry-run_the_address_lint_before_publishing import_publish.py_and_run_the_gate_function 5_hits_vs_0_hits check_a_gate_by_running_the_gate _personal_email_hits_default_argument _base_ref_email_addresses_closure the_helper_disagrees_with_run_gate my_fixtures_look_like_blockers_but_are_grandfathered", ocd: 2026-09-03, lmd: 2026-09-03] DO NOT dry-run a gate by hand-writing a regex that approximates its predicate, and DO NOT call its helper with default arguments, BECAUSE the gate's real answer lives in the WIRING, not the helper: `_personal_email_hits` defaults `known_for` to `lambda _: frozenset()`, but `run_gate` passes `_base_ref_email_addresses` per file — measured 2026-09-04, the stub reported 5 blocking hits where the real gate reported 0. DO import `scripts/publish.py` and call its own functions with the same arguments `run_gate` builds (`_added_lines_since(root, base)` + a `known_for` closure over `_base_ref_email_addresses`); a 30-second script beats a 10-minute publish attempt.
[^18]: [id: ATOM-OVFB-124R, status: valid, keywords: "publish_suddenly_blocked_on_fixtures_that_were_always_there renamed_a_test_file_and_the_address_lint_exploded five_inexplicable_hits_after_a_refactor grandfathered_addresses_stopped_being_grandfathered git_show_base_ref_path_returns_nothing_for_a_new_path moving_a_fixture_file_blocks_the_release the_same_addresses_passed_yesterday per-file_known_address_exclusion_breaks_on_rename address_lint_false_positive_after_moving_tests why_did_the_lint_flag_an_unchanged_fixture", ocd: 2026-09-03, lmd: 2026-09-03] DO NOT assume an allow-listed-by-history address stays allow-listed when you MOVE or RENAME the file holding it, BECAUSE `_base_ref_email_addresses` resolves `git show <base_ref>:<path>` and returns an EMPTY set when that command fails — and at a path the base ref does not have, it always fails. Whether that BITES depends on git rename detection, which `_added_lines_since` does not disable: a pure rename emits no content hunks at all (no added lines, no hits); a rename plus a small edit is still reported as a rename, so only the EDITED lines are scanned; but a rename plus a rewrite below the similarity threshold degrades to delete+add, every line reads as added, `known_for` at the new path is empty, and then every address in the file flags at once. Only that third case produces the pile of inexplicable hits. Derived from the code (scripts/publish.py:959 and the `returncode != 0` guard), not yet observed in a run. DO expect a rename of a fixture-heavy module like `tests/test_oauth_rotator.py` to surface every address it has ever held, and either rewrite those fixtures to assemble around a split `@` in the same commit, or split the rename from the content change.
