# env-secret-on-disk-detector


^ATOM-VMZD-QTYQ [desc: "env-secret-on-disk searches files for the exact secret values of the session environment and raises CRED-002 with name, path, line and fingerprint, never the value", keywords: environment_printed_into_a_file secret_from_environment_found_on_disk CRED-002_finding env-secret-on-disk_detector_what_it_does janitor_issue_354_env_dump_to_file env_secrets.py_matcher_needles exact_value_search_no_pattern detector_is_report-only_never_rewrites_a_file keyed_fingerprint_of_secret_value run_env-secret-on-disk_by_hand_after_a_slip delete_env-secret-on-disk.cursor.json_for_a_full_pass, type: reference, trdd: TRDD-ZANQ1QW0, ocd: 2026-11-19, lmd: 2026-11-19]

scripts/detectors/env-secret-on-disk.py (matcher and sweep in scripts/lib/env_secrets.py, variable-name logic in scripts/lib/secret_names.py) finds the live secret VALUES of the running session's environment in the folders agents write to. Why (janitor issue #354, second event of its class): a command that printed a process environment with its output redirected into a scratch file left the whole session environment on disk; the Bash guard (scripts/lib/env_dump_guard.py, a2e5807c) lowers the rate, and this sweep catches what passes the guard with no pattern, because the session knows its own secrets exactly and searches for those bytes. REPORT-ONLY: it never rewrites, moves or deletes a file (in-place redaction of untracked files is irreversible and was left to the owner); a finding (CRED-002) carries the variable NAME, path, line and a keyed fingerprint (a salted hash of the whole value, one salt per installation, stable across sessions), never the value. Needles are secrets of 16 or more characters with at least 8 distinct characters; the needle table lives in memory only. Limits stated in every finding: an overwritten file can survive in snapshots and backups, a value already printed into a conversation has already been sent, and a transformed secret (compressed, split, encrypted) is not found. It does NOT use state.is_self_scan_target(): that guard exists because pattern scanners flag the janitor's own fixtures, and an exact-value matcher has no fixtures to match; skipping the janitor's own repo would blind the sweep where agents write the most scratch. Run it by hand right after a slip with uv run on scripts/detectors/env-secret-on-disk.py; for a full pass from the newest file delete .janitor/state/env-secret-on-disk.cursor.json first (regenerated state) and repeat until the log says 0 left for the next pass.


^ATOM-U2XI-F7UJ [desc: "the sweep is bounded: 60 s budget including a 30 s listing share, trash batches read by name in 15 s, so a pass cannot reach the 120 s detector kill", keywords: env-secret-on-disk_pass_too_slow detector_killed_at_120_seconds listing_cut_after_N_s_cursor_kept TIME_BUDGET_S_LISTING_BUDGET_S_env_secrets.py trash_batch_read_by_name_not_mtime secret_moved_into_.trashcan_never_read safe-delete_keeps_old_mtime trashcan_names.py_shared_with_trashcan-purge TRASH_SETTLE_S_batch_younger_than_120_s coverage_line_printed_once_per_day sweep_trash_saved_position_path_components, type: reference, trdd: TRDD-ZANQ1QW0, ocd: 2026-11-19, lmd: 2026-11-19]

A pass used to list about a million files and read for minutes (reading under load measured about 9 MiB/s, so one 256 MiB file takes about 30 s) and could run into the detector's 120 s kill, which writes no state so the next pass repeats the same reads. TRDD-ZANQ1QW0 (issue 354) bounded it in five increments, constants in scripts/lib/env_secrets.py: (1) .trashcan timestamp batch folders are no sweep roots; sweep_trash reads settled batches (older than TRASH_SETTLE_S = 120 s) BY NAME, newest first, each from its own saved position, with TRASH_TIME_BUDGET_S = 15 s and TRASH_BYTE_BUDGET = 64 MiB (54674cc4; the old mtime walk listed 951,892 files in 26 batches and took 19.45 s of a 28.08 s walk, and it NEVER saw a file moved into the trash because safe-delete keeps the old mtime; positions are tuples of path components because a joined-string compare sorts "a-b" before "a/x" and would skip a file; scripts/lib/trashcan_names.py holds the batch-name parsing shared with trashcan-purge.py); (2) the clock starts before the listing and TIME_BUDGET_S = 60 s covers listing and reads, listing share LISTING_BUDGET_S = 30 s, clock read once per folder and every 1024 files (9a1cea8c); a cut listing reads nothing, keeps the cursor and retry counts, withdraws no finding, logs "listing cut after N s, cursor kept" and prints the coverage line once per local day, because an mtime cursor may move only over a COMPLETE listing; (3) newest change first from a covered range (c0e14873); (4) one pass at a time per project (3181a0ea); (5) a hard read bound (0db48c58).


^ATOM-SHH7-KNWK [desc: "the sweep keeps a covered range of mtimes and reads the newest changes first, so a leak in a file changed today is read on the next pass", keywords: fresh_leak_waited_250_passes env-secret-on-disk_covered_range_lo_hi read_newest_file_first FRESH_SHARE_half_of_the_budget LIVE_EDGE_MARGIN_S_file_written_during_listing old_cursor_key_dropped_not_migrated file_moved_in_with_old_mtime_not_seen state_file_env-secret-on-disk.cursor.json_covered_flagged_retries_trash MAX_FAIL_RETRIES_holds_the_range backlog_read_newest_first_descending, type: reference, trdd: TRDD-ZANQ1QW0, ocd: 2026-11-19, lmd: 2026-11-19]

Read order (c0e14873): the old sweep read oldest change first from one cursor, and on this repo 455,681 files sat behind it at about 1,850 files per pass (including a 199,366-file scratch copy under reports_dev), so a fresh leak in a file changed today waited about 250 passes. State is now a covered range [lo, hi] of (mtime, path) keys, every key inside it read. A pass reads two tiers: keys ABOVE hi ascending with FRESH_SHARE = 0.5 of the byte budget and of the time left after the listing, then the backlog BELOW lo descending (newest first) with the rest; each tier reads at least one file per pass so one fresh file larger than the whole budget cannot stop the backlog. hi never moves above the live edge (wall time at listing start minus LIVE_EDGE_MARGIN_S = 2 s): a file written during the listing into an already walked folder has a later mtime and an hi moved past it by a newer file would cover it unread. Holds go to their own edge, a failing file holds the range up to MAX_FAIL_RETRIES = 3 passes. The old "cursor" key is dropped, not migrated (migrated as [(0, ""), cursor] it would make every file above it the fresh tier, read oldest first); an absent "covered" key starts at the live edge and keeps flagged, retries and trash. Known limits: a file moved in with an old mtime INSIDE the range already read is not seen until the state file is deleted, and a future-dated file is re-read every pass inside the fresh share.


^ATOM-T5PP-ZUNF [desc: "a hard 75 s read deadline cuts a big file mid-read; an flock on env-secret-on-disk.lock lets one pass run per project at a time", keywords: detector_read_one_big_file_past_120_s hard_deadline_s_75_main_25_trash scan_file_deadline_cut_partial_hits SweepReport.cut_cut_given_up read_again_next_pass_log_line_wrong two_sessions_ran_env-secret-on-disk_at_once env-secret-on-disk.lock_flock_non-blocking cursor_file_overwritten_flagged_list_lost per-phase_seconds_on_the_pass_line trash_file_over_200_MiB_cut_on_every_try killed_pass_writes_no_state, type: reference, trdd: TRDD-ZANQ1QW0, ocd: 2026-11-19, lmd: 2026-11-19]

Hard read bound (0db48c58): the byte and time budgets were checked only BEFORE a read and each tier reads at least one file whatever they say, so the first files of the fresh tier, the backlog and the trash walk could add up to about 135 s, over the 120 s kill. scan_file now takes an optional deadline and clock and checks it before every chunk after the first, returning (hits, cut); a cut is reported only when bytes are left. _read_one keeps the partial hits of a cut file, lists it in SweepReport.cut (not unreadable, not read, not counted in scanned or bytes_read) and returns it like a failed read so hold and retry apply and a flagged file keeps its CRED-002 finding; a cut file already given up on goes to cut_given_up. sweep and sweep_trash take hard_deadline_s counted from each sweep's own start: 75 s main, 25 s trash, checked before every read; a cut ends that sweep and the backlog does not start after a hard stop of the fresh tier. The library default is None; only the detector opts in. Known limits: 75 + 25 s assume the default 120 s detector timeout, and a trash file over about 200 MiB cannot be read inside 25 s, so it is cut on every try, given up and counted on the coverage line. e1184b6e: the "cut by the hard read bound, read again next pass" log line lists only cut paths NOT in report.cut_given_up (given-up files are not read again until they change); f2c70baa adds per-phase seconds (listing, fresh, backlog, trash, total) to the pass line. One pass at a time (3181a0ea): dispatch.py stamps last-run only after the detector returns and no lock covered a heartbeat fire, so two sessions of one project sharing the cron minute could each rewrite the one cursor file whole and drop the other pass's flagged list, retries and positions; main() now takes an exclusive non-blocking flock on a separate never-renamed file .janitor/state/env-secret-on-disk.lock (the cursor is replaced by rename so it cannot carry the lock), held from before the cursor read to after the write; a pass finding it held logs one line, prints nothing and returns 0.


^ATOM-V1WM-X0OJ [desc: "a CRED-002 finding is withdrawn only for a fingerprint this pass held and found absent in a file it fully read; old state loads as unknown and never withdraws", keywords: CRED-002_issue_closed_but_value_still_on_disk finding_withdrawn_for_a_file_never_read flagged_state_fingerprints_unknown_sentinel withdraw_finding_only_when_pass_held_the_secret another_session_environment_lacked_the_secret secret_rotated_finding_stays_open SweepReport.read_fully_read_paths flagged_file_deleted_trash_copy_keeps_finding Hit.fingerprint_salted_hash old_bare-path_state_entry env-secret-on-disk_withdraws_finding_wrongly, type: reference, trdd: TRDD-ZFD3KBM3, ocd: 2026-11-19, lmd: 2026-11-19]

When a CRED-002 finding is withdrawn (TRDD-XNZFKX0L, TRDD-ZFD3KBM3): the state's flagged map is path to the sorted fingerprints of its secrets (Hit.fingerprint). After a pass a recorded fingerprint is dropped only when the file was FULLY read this pass (SweepReport.read, filled by _read_one only in its success branch when the exact matcher ran, both tiers), this pass HELD that same secret, and no hit came back for it; the path is withdrawn when its list is empty. Before 9f9e7f5d the detector withdrew a finding for every flagged path in keys (processed plus failed) or the trash processed set, which also hold a file whose read failed, a file over MAX_FILE_BYTES and a file given up on, and a pass with no secret in its environment scans nothing, so each of those cleared an issue about a file never checked. Before d611dea0 a finding was withdrawn when the file was read clean even if THIS pass's environment lacked the secret behind it (the matcher is built from the process environment, the state file is shared by every session of the project), so a pass after a rotation or from another session withdrew a finding whose value was still on disk. A state entry from before the change is a bare path that cannot name its secret: it loads as the sentinel ["unknown"], never in a live set, so no read withdraws it and it closes only when the file is gone. A flagged file that no longer exists (lstat FileNotFoundError) is withdrawn only when no copy sits under <project>/.trashcan/<child>/<path relative to the project>, the place safe-delete moves it to; any other OSError or an unlistable trash keeps the finding; a path outside the project gets no lookup (os.pardir check). Known limit: a rotated secret closes only when the file is gone.



^ATOM-6ZI6-LWW7 [desc: "env-secret-on-disk runs hourly from the heartbeat (env_secret_on_disk_interval 3600 s), is deferred under host pressure and listed as a security detector", keywords: how_often_does_env-secret-on-disk_run env_secret_on_disk_interval_option hourly_detector_in_dispatch.py_roster _PRESSURE_HEAVY_DETECTORS_deferred_under_pressure env-secret-on-disk_missing_from_doctor_output security_detectors_never_filtered_as_advisory test_env_secret_on_disk_registration detector_count_79 quiet_heartbeat_filter_env-secret env-secret-on-disk_not_running_on_a_schedule, type: reference, trdd: TRDD-ZANQ1QW0, ocd: 2026-11-19, lmd: 2026-11-19]

The detector ran only on demand until 64880ea5 (TRDD-ZANQ1QW0) because a pass could stall a fire; once the lock and the hard read bound existed it joined the heartbeat. scripts/dispatch.py has an hourly roster row (option env_secret_on_disk_interval, 3600 s, declared in .claude-plugin/plugin.json) and the detector is in _PRESSURE_HEAVY_DETECTORS, so a host under pressure defers it and a deferred detector stays due and runs on a later fire. scripts/commands/doctor.py, scripts/fleet_status.py and tests/test_quiet_heartbeat.py list it with the SECURITY detectors, so it is never filtered as advisory noise. tests/test_env_secret_on_disk_registration.py pins the row (exactly once, that interval) and the heavy-set entry. The roster count became 79 detectors (janitor-detector-and-hook-roster-list). Detector-side env git calls resolve git through exe() (see bandit-sweep-and-exe-helper).


^ATOM-SYSL-1ZSC [desc: "env_dump_guard.py denies Bash commands that print a process environment unless reduced to names or a count; secret_names.py copies the shield name regexes", keywords: Bash_command_printed_the_whole_environment ps_eww_redirected_to_a_file env_dump_guard.py_denies_printenv_env_export_-p printenv_NAME_denied_for_secret_names secret_names.py_SECRET_NAME_copy_of_patterns.ts ENV_EXTRA_NAME_pat_cookie_oauth_bearer_key janitor_env.py_prints_environment_with_values_hidden pre_bash_safety_enabled_opt-in_guard_inert pre-bash-safety.py_imports_env_dump_guard_at_module_level issue_354_second_layer_guard GH_PAT_SESSION_COOKIE_CLAUDE_CODE_OAUTH_TOKEN_names, type: reference, trdd: TRDD-G14LKPEC, ocd: 2026-11-19, lmd: 2026-11-19]

Issue #354 had a second layer besides the sweep: `ps eww -p N > file` left the session environment on disk and the Bash guard let it through (ps is not an exfil source and no network sink followed). a2e5807c (TRDD-G14LKPEC) added the pure guard scripts/lib/env_dump_guard.py, called from scripts/hooks/pre-bash-safety.py: it denies env, printenv, ps e or -E, export -p, set, declare -x, /proc/N/environ, pm2 env and inline whole-environment reads UNLESS the same pipeline reduces them to a count or to names; here-document bodies run by a shell or interpreter, shell keywords, substitutions, here-strings and assignments are followed; printenv NAME is denied for secret names. scripts/lib/secret_names.py is the one "this variable holds a secret" test shared by the guard, the live-value matcher and the helper: SECRET_NAME, NOT_SECRET_NAME and STRONG_NAME are copies of the same three expressions in hooks/secret-shield/patterns.ts (tests/test_secret_names.py compares their source text so they cannot drift), plus ENV_EXTRA_NAME for names the shield list lacks (pat, cookie, oauth, bearer, bare key: GH_PAT, SESSION_COOKIE, CLAUDE_CODE_OAUTH_TOKEN); moving those words into patterns.ts belongs to TRDD-Q6LPJTPO. scripts/janitor_env.py is the legitimate alternative: it reads one process environment in memory and hides every value except allowed names, never a secret-named one. The guard is opt-in: main() returns before any check while pre_bash_safety_enabled is false, so it is inert by default; the hook imports env_dump_guard at module level before that check, so an import failure would break the hook even when off. Fuzzed in scratch for crashes and time only (60,009 inputs, 0 exceptions, worst 0.115 s); 4,907 inputs were newly denied against the old guard and not sampled.
