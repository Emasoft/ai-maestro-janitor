# secret-shield-scan-skill


^ATOM-DQ9C-1P48 [desc: "scripts/shield_scan/scan.ts scans a tree with the shield core in killable worker processes and writes a findings file with no secret values; exit 3 means incomplete", keywords: scan_a_project_for_secrets janitor-secrets-shield-scan_skill scan.ts_findings_file shield_scan_scan.ts_worker.ts_fileset.ts scan_exit_code_3_incomplete findings_file_refused_inside_git_work_tree scan_never_prints_a_secret_value per-file_time_limit_SIGKILL_worker files_scanned_mb_per_s_summary_line scan_leaked_API_keys_in_a_folder_tree shield_scan_passes_secrets_cards_email_home, type: reference, trdd: TRDD-BAQB9SYO, ocd: 2026-11-19, lmd: 2026-11-19]

The skill skills/janitor-secrets-shield-scan/SKILL.md runs scripts/shield_scan/scan.ts (the driver) under bun. scan.ts builds the file set (scripts/shield_scan/fileset.ts), starts child processes that run worker.ts, and writes one JSON line per finding, skip and the final summary to a findings file that holds paths, kinds and line numbers, never a secret value. It applies the shield core through redactAll (hooks/secret-shield/pipeline.ts, no pass order of its own) with the passes of --passes (secrets and cards by default; email and home opt-in). Why child processes with a per-file SIGKILL: the core passes are synchronous regexes, so a pathological file cannot be interrupted from its own thread; the driver kills the worker at base + per-MB seconds (default 30 s + 5 s per MB) and starts a new one, and a kill after the whole-file reply keeps the counts with line null (32cc16f5, TRDD-BAQB9SYO). The findings file is mode 0600 and a path inside any git work tree is refused with exit 2, because the file says where the secrets are and a commit would publish that. Exit codes: 0 complete and no findings, 1 complete with findings, 3 incomplete (a timeout, read-error, crash, git-error or unreadable-dir skip), 2 usage or fatal. A run is never called clean when complete is false. Not built yet (open cards): git history scan (TRDD-QWD53NHM), a Rust accelerator (TRDD-LJSST2WL), a large lane for scan-only (TRDD-VD8UAXGF). Tested on macOS only; needs bun and git on PATH.


^ATOM-ZLAV-H3QL [desc: "the scan respects .gitignore by default; ignored_repos, gitignored_entries and ancestor_rules_skipped say what was not scanned, --all scans everything", keywords: scan_skipped_ignored_folders gitignored_entries_ignored_repos ancestor_rules_skipped_true scan_--all_hidden_and_ignored_files scan_root_inside_an_ancestor_repo why_a_default_scan_read_872136_files scan_respects_gitignore_by_default git-error_skip_of_dot fileset.ts_walkRepo_ls-files git_config_fsmonitor_false_in_scanner run_not_clean_when_part_of_tree_not_scanned, type: reference, trdd: TRDD-BAQB9SYO, ocd: 2026-11-19, lmd: 2026-11-19]

Scope follows ignore rules: a repo is listed with git (core.fsmonitor=false, so a repo-configured fsmonitor command never runs), ignored folders and the repos inside them are not scanned, and --all scans every file plus each repo's .git/config (a remote URL can hold a token) but never other .git content. A root with no .git of its own under an ancestor repo is probed with git ls-files -co --exclude-standard -z (08a8e8f2): if the ancestor leaves anything listed its ignore rules apply, if it hides everything the root is walked as a plain folder and the summary field ancestor_rules_skipped is true; a git failure is a git-error skip of "." and exit 3, never a walk. Summary fields that say what was NOT scanned: gitignored_entries, ignored_repos (repos found by lstat one level into ignored folders; a repo two or more levels below is not counted) and ancestor_rules_skipped; the report must name them and --all, never call the run clean. History: e3a058a9 first scanned clones inside ignored folders by default and read 872,136 files instead of 2,786 on one repo (about 186 cloned repos under ignored scratch folders), so 92eb3472 reverted it to honor the owner order "gitignore is respected by default; only an option scans everything". Symlinks are never followed; entry types come from lstat, not readdir. Known limits recorded in spec D5: a root the ancestor tracks nothing under that holds only untracked files is walked plain.


^ATOM-7SLQ-VYWI [desc: "scan.ts --redact swaps secrets for UUID markers and keeps values in a plain vault at ~/.secrets_shield/vault.db; a file is written only after the restore check passes", keywords: scan_--redact_marker_REDACTED-BY-SECRET-SHIELD_Type_ID where_is_the_vault_db vault_is_plain_text_not_encrypted redact_rewrites_working_tree_files redact_skip_reasons_recent_hardlinked_not-utf8_git-operation findings_not_redacted_residual_exit_1 redact_rounds_at_most_3_residual home_pass_last_not_restorable_home_rewrites redact_does_not_remove_secrets_from_git_history align-error_restore_check_byte_for_byte redact.ts_worker.ts_redactFile_order, type: reference, trdd: TRDD-BAQB9SYO, ocd: 2026-11-19, lmd: 2026-11-19]

scan.ts --redact (worker.ts plus the pure redact.ts) replaces each secret with [REDACTED-BY-SECRET-SHIELD. Type: <type>. ID: <UUID>] and keeps the value in a plain, unencrypted SQLite vault at ~/.secrets_shield/vault.db (owner decision TRDD-QM8YRCZ5: the vault must work unattended, so the restricted file modes were dropped; anyone who can read the account files reads every value). The same value in one file gets one ID and a second run changes nothing. A value never leaves the worker process: the driver gets counts, kinds and fixed-text outcomes only. Order inside redactFile (acd033ae, 0c52f0b3, 2923a7e7, c6007279): cut the markers already in the text, run the passes on each stretch between them, align output to input to recover the replaced text, sweep other copies of a hidden value, re-scan (up to 3 rounds; what is still found is the residual, the file is still written and the run exits 1), run the optional home pass last (it writes no marker, is not vaulted and not restorable, counts as home_rewrites), check that the vault can restore the original byte for byte (else skip align-error), then commit the vault rows and write the file atomically. A file is written only after every check that can skip it. Skip reasons that leave the file unchanged and count in findings_not_redacted: git-internal, vault-folder, hardlinked, recent (modified within --min-age-minutes, default 10), not-utf8, git-operation (merge, rebase, cherry-pick, revert or bisect in progress), git-check-failed, align-error, json-broken, not-regular-at-write, outside-root, vault-conflict, changed-during-redact, write-error. Redacting tracked files changes only the working tree: every committed secret stays in git objects and checkout, stash or reset brings it back; history is never rewritten (owner decision).


^ATOM-ZSOY-6KAM [desc: "vault rows are committed once per file right before the write, so a skipped file leaves no row; a failed write leaves rows with no marker", keywords: vault_rows_with_no_marker redact_skip_leaves_plaintext_rows_in_vault.db vault-conflict_skip insertPlanned_BEGIN_IMMEDIATE_transaction vault.lookup_read_only_planned_uuid write-error_leaves_vault_rows SQLITE_BUSY_opening_a_new_vault vault_home_from_dscl_not_HOME vault.ts_lookupOrInsert_UNIQUE_origin_value_encoding bun_vault.ts_list_delete 2_TB_redact_run_leaked_values_into_vault, type: reference, trdd: TRDD-JYZAL6HW, ocd: 2026-11-19, lmd: 2026-11-19]

Vault rows are written ONCE per file, as the last step before the atomic write, after every check that can skip the file (restore check, broken JSON line, later round, home pass, write target). Before c6007279 (TRDD-JYZAL6HW), redactFile called vault.lookupOrInsert in every round, so a file skipped at a late check kept its original text AND left plaintext rows that no marker pointed at: on a 2 TB run every such skip leaked a value into vault.db. Now each round plans one uuid per distinct value (vault.lookup is read only: the row an earlier run left, else a fresh randomUUID) and vault.insertPlanned commits all rows of the file in one BEGIN IMMEDIATE transaction right before writeAtomic; it compares each returned uuid with the planned one and reads each row back (value, encoding, origin), and any difference rolls the whole file back and skips it as vault-conflict. Rows still remain, by design, when writeAtomic fails after the commit (write-error, changed-during-redact) or the process is killed between commit and rename: the commit stays before the write so a crash leaves a row with no marker, never a marker with no row; restore never reads such rows and a later run reuses them (one row per origin and value). Vault module facts (acd033ae): one table with UNIQUE (origin, value, encoding), WAL with a 10 s busy_timeout set before WAL (8 worker processes opening a NEW vault at once failed 10 of 160 opens with SQLITE_BUSY, 0 of 160 on an existing one, so scan.ts opens the vault once before the workers start), and the account home comes from the account database (dscl, getent), never HOME, because os.userInfo().homedir follows HOME under bun.

^ATOM-99R1-KJAK [desc: "restore.ts restores by uuid only in the origin file, only from a terminal, and is never run by an agent; unknown-encoding leaves the marker and exits 1", keywords: restore.ts_refuses_to_run_stdin_not_a_terminal restore_a_redacted_file marker_reported_as_moved_--any-origin unknown-encoding_marker_left json-string_vault_encoding_removed restore_only_in_the_file_it_came_from changed-during-restore_skip restore_skips_binary_file_NUL_probe restore_exit_codes_0_1_2_3 agents_never_run_restore.ts restored_value_back_from_vault type-mismatch_note_on_restore, type: reference, trdd: TRDD-BAQB9SYO, ocd: 2026-11-19, lmd: 2026-11-19]

scripts/shield_scan/restore.ts (0f96e75c) puts the vaulted value back in place of each marker of one file or every file under a folder; it is for a person at a terminal only and agents never run it. Rules and their WHY: restore by uuid alone (a value found under two kinds shares one row with its first kind; a differing Type is a type-mismatch note); a row is restored only in the file it came from unless --any-origin, because a marker copied to another file would write the secret there (a moved or copied project needs --any-origin; another hard link of a redacted file reads as moved); with the real vault stdin must be a terminal, which stops an accidental or unattended run but is not a boundary (a pseudo-terminal passes); the vault file is checked before openVault because openVault creates a missing vault and a restore must not; the first 8192 bytes are probed for a NUL before the whole read (a big binary would otherwise be read whole), and a binary file is left alone; the redact worker's write guards apply in the same order (hardlinked, git operation, write target, atomic write) EXCEPT the recent-file guard, since after a restore an editor saving its old buffer writes only markers back and a re-run restores them; a read whose length differs from the stat is skipped as changed-during-restore; every error is fixed text. A marker whose vault row has an encoding other than raw is left and reported as unknown-encoding, and the run goes on with exit 1 (1c42d3c2: the json-string encoding was dropped, spec v6 writes every vault value raw, the encoded substring of its JSON token, so exact original bytes go back; an old vault keeps its CHECK and still works; a fatal error was rejected because it would stop the run after earlier files were already restored, with no summary). Restore exits: 3 incomplete (wins over 1), 1 a marker was left or a file with markers was skipped, 0 all restored, 2 usage, refused or no vault.


^ATOM-GSKG-HP8V [desc: "jsonl.ts plans JSONL redaction over decoded JSON strings and maps stretches back to encoded bytes; json-broken and align-error are the skip reasons", keywords: redact_jsonl_transcript_file skip_json-broken skip_align-error_jsonl json-unredactable_finding_kind jsonl_lines_not_json_summary_field planJsonl_jsonlHits_jsonl.ts sentinelMarkers_shield_marker_opaque secret_behind_JSON_escape_in_a_jsonl_file round_2_read_shield_markers_as_values scan_of_a_redacted_jsonl_found_connection-string_password_in_marker jsonl_file_timeout_skip_no_findings_kept finalTextAligned_brokenLines, type: reference, trdd: TRDD-BAQB9SYO, ocd: 2026-11-19, lmd: 2026-11-19]

A .jsonl or .ndjson file is read and redacted JSON-aware in both modes by scripts/shield_scan/jsonl.ts (planJsonl, jsonlHits; one walk feeds the whole-file counts, the per-line locations and the residual). Each line that parses as JSON is searched in its decoded strings (a secret behind an escaped newline, slash, quote or a backslash-u sequence is found) via redactJsonLine; the replaced stretch is mapped back through the escapes of the original token to its ENCODED substring, so the vault holds the exact original bytes (619abb6f). A maximal run of consecutive non-JSON lines is planned as one plain text, so a PEM key in a .jsonl that is not really JSONL is still hidden whole; such lines are counted in jsonl_lines_not_json. A redactJsonLine throw counts one hit of kind json-unredactable for its line (otherwise a file whose only finding was on that line would end clean); skipReasonOf maps causes to json-broken (the shield cannot hide a finding without breaking the line, or a sweep copy written right after a backslash would break a line that parsed before) or align-error (5da85ccc, c6270b48). The worker checks brokenLines of each round text after the restore check; finalTextAligned writes each marker followed by the newlines of its value so line numbers stay comparable. Shield markers are opaque to the planner: sentinelMarkers swaps every raw core marker and shield marker for a nonce marker before planning (e1ac16d0), because round 2 had read shield markers as values (a connection-string rule took the first word of a marker for a password and a gitlab-session-cookie hit fired), giving 94 residual hits and a null plan that skipped one real transcript of six as align-error. Consequences: a value glued right after a marker is not counted, and text shaped like a marker is never read. Time limit: one walk per file, so a file past the per-file limit is a timeout skip (exit 3) with no findings kept; cost about 350 ns of CPU per byte measured once on loaded hardware (indicative). A card number written as a JSON number is not read.

^ATOM-AAX7-QWDF [desc: "the large lane redacts text files over 64 MB one at a time up to 1024 MB; SHIELD_SCAN_VERSION lets a vendored scan.ts report its version without a manifest", keywords: scan_large_file_out_of_memory not-scanned-too-large_exit_3 --max-large-mb_--max-file-mb large_lane_one_worker_at_a_time redact_needs_13_times_file_size_in_memory SHIELD_SCAN_VERSION_set_but_empty_or_malformed SECRETS_SHIELD_SCAN_VERSION_renamed vendored_scan.ts_has_no_plugin_manifest plugin_version_summary_field big_binary_probed_for_NUL_8192_bytes report-sanitizer_vendored_copy_of_scan.ts, type: reference, trdd: TRDD-BAQB9SYO, ocd: 2026-11-19, lmd: 2026-11-19]

Large lane (2923a7e7): with --redact, a text file over --max-file-mb (default 64) and up to --max-large-mb (default 1024) is redacted by one dedicated extra worker fed through a queue, one such file at a time, because a worker holds the whole file several times over (buffer, decoded string, redacted copy) and jobs times that could exhaust the host (it froze once). A file over --max-file-mb is probed for a NUL in its first 8192 bytes first, so a big binary stays an ordinary binary skip and is never read whole. Text over --max-large-mb is neither scanned nor redacted: skip not-scanned-too-large, files_not_scanned above 0, exit 3. Measured once per size on generated text with about one secret per 100 KB: 100 MB took 36 s and 300 MB took 592 s; the redact worker needed at least about 13 times the file size in memory (a sampled lower bound) and restore about 4 times; time grew faster than size (cause not found), so a text file over about 300 MB with many secrets may run past its per-file limit. On a low-memory machine pass a lower --max-large-mb. Without --redact the over-size skip is unchanged. SHIELD_SCAN_VERSION (environment; first named SECRETS_SHIELD_SCAN_VERSION in aac4efb4, renamed in a98fc716): when set it replaces the manifest version as summary plugin_version, for a byte-identical vendored copy of scan.ts that has no .claude-plugin/plugin.json (the report-sanitizer merge); a value that is empty, over 64 characters or holds whitespace or a control character exits 2 with a fixed text, with no fallback to the manifest; the version and the core hash are read right after the arguments and the git check, before the findings file or the vault is opened, so a bad value cannot leave a --redact run half done.
